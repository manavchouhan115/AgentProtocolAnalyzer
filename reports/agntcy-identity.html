Summary

AGNTCY Identity is a specification for giving AI agents, MCP servers and multi-agent systems a universally unique ID backed by a signed credential, so others can check who published them and that their definition has not been altered. It is aimed at the 'Internet of Agents', where one agent discovers and composes others from different organisations. It is maintained in the AGNTCY project, an open-source collective under the Linux Foundation started by Cisco. The spec is published as a documentation site and Git repository with v1alpha1 APIs and no versioned release. Cisco's Outshift runs a hosted Identity Service built on it.

An organisation brings an existing ID for its agent (e.g. an Okta application ID or an A2A Agent Card) or gets a DID from an AGNTCY Identity Node. It signs an 'Agent Badge', a W3C Verifiable Credential wrapping the agent's OASF or A2A definition, and publishes the badge and a ResolverMetadata record with its public keys to an Identity Node. A party that wants to use the agent resolves the ID, fetches the badge and verifies the signature, typically at discovery time before connecting. Badges can be revoked at the node. The spec does not define how an agent proves, on a request, that it is the agent named in a badge. It also leaves out user delegation, scoped permissions, contact details and model identity.

How it works

  1. An agent creator (an organisation or sub-organisation) creates a key pair in a wallet or vault, and registers its issuer details with an Identity Node, optionally proving ownership of its domain or IdP identity.
  2. The creator gives the agent an ID: either one it already has (e.g. an Okta app ID, a Duo or Entra ID client ID, or an A2A well-known URL) or a did:agntcy DID generated by the Identity Node, which also publishes a ResolverMetadata record with the verification keys.
  3. The creator puts the ID into the agent's definition (an OASF record or A2A Agent Card), signs a Verifiable Credential over it (an Agent Badge with a Data Integrity proof or JOSE envelope), and publishes the badge to the Identity Node.
  4. A consumer (a person, a client, or another agent) discovers the agent, e.g. through the AGNTCY directory, and extracts its ID.
  5. The consumer resolves the ID at the Identity Node to get the badges and ResolverMetadata, picks the badge matching the definition, and verifies its proof with the issuer's public key. The node can also report whether the badge was revoked.
  6. The consumer decides whether to trust and connect to the agent. Authenticating the connection itself is left to other mechanisms (e.g. OAuth via the IdP).

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
A consumer can check, before connecting, that an agent's definition was signed by a named organisation and has not been changed. The spec gives services nothing to tie a live request to that agent or to limit what it may do.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
The issuer can irreversibly revoke a badge (one agent version) at the Identity Node, and verifiers that check the node will see it. Services that verified earlier are not notified, and services cannot report an agent.

Accountability

Goal: an action can be traced back to the parties responsible for it.
A verified badge traces the agent's definition to an issuing organisation, optionally with verified domain ownership. It does not identify a user, an instance or the model.

Not addressed

  • Agent instance identifier: No (not addressed by the specification)
  • Acting for (authority): No (not addressed by the specification)
  • Credential type: Badge VC exists, but not sent on requests (not addressed by the specification)
  • Credential lifetime: Unspecified (not addressed by the specification)
  • Authentication of the agent or user: No; verifies the issuer's signature (not addressed by the specification)
  • Scoped authorization: No; TBAC lives in the separate Identity Service (handled outside the protocol)
  • Human approval: None (not addressed by the specification)
  • Contact and escalation: None (not addressed by the specification)
  • Cross-party signalling: None (not addressed by the specification)
  • Model identity: No field defined (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Not addressed
No credential on requests. The spec's credential is an Agent Badge: a W3C Verifiable Credential whose subject is the agent's ID and definition, signed by the issuing organisation with a Data Integrity proof or JOSE envelope. Badges are published at an Identity Node and fetched by whoever wants to check the agent. The agent does not send them with its requests. A Verifiable Presentation model exists in the data model, but no flow uses it. A public badge also does not prove the presenter is the agent, because anyone can fetch and replay it.
Not addressed by the specification

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Partly addressed
Partly. The Identity Node API has an irreversible Revoke call, which needs proof of the issuer's ownership, and the data model includes a W3C credentialStatus entry with a revocation purpose. Verification through the node can then return a 'revoked' error. Revocation is per badge, i.e. per agent definition or version, and is done by the issuer. The spec does not say when verifiers must re-check status. Because badges are typically verified before connecting, a consumer that already trusted the agent is not notified.
Part of the normal flow
Why this rating: Revocation is defined, but nothing requires verifiers to re-check it, so it does not reliably reach every party that verified earlier (the calibration examples are red because they define none).

Notes

  • The specification does not use RFC 2119 keywords. MUST* in the identifier row reflects the descriptive statement that each agent subject has a universally unique ID (lowercase-style requirement).
  • The spec is a documentation site plus generated API docs (protobuf, JSON Schema, OpenAPI). Several parts are explicitly incomplete, e.g. the role of Identity Nodes, and the commented-out 'Agent Passport' text in the introduction is an earlier name for the badge.
  • The architecture page describes the Resolver as 'decrypting' the ProofValue. Data Integrity proofs are signatures that are verified, not decrypted. The flows describe verification correctly.
  • The AGNTCY Identity Service (agntcy/identity-service) and the agntcy/identity implementation add features such as TBAC policies. They are implementations and products, not part of this spec, and were not counted.
  • No page on the site contained instructions aimed at AI tools.

Open questions

  • How is an agent expected to prove at runtime that it is the subject of a badge (e.g. a Verifiable Presentation signed with a key in the ResolverMetadata verificationMethod)? The data model allows it, but no flow defines it.
  • What trust policy should a verifier apply to Identity Nodes and unverified issuers? The spec defers this to future updates.
  • Should verifiers re-check revocation status before each connection or on a schedule?
  • Is an expiry expected on badges? Examples carry only validFrom.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (47 of 47 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-20. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
