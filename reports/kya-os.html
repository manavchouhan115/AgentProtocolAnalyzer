Summary

KYA-OS (Know Your Agent Operating System, formerly MCP-I) adds identity, delegation and audit proofs to AI agents calling tools, first of all MCP servers. It answers three questions for the receiving server: who is calling, under whose authority, and what was done. Vouched wrote it and donated it to the Decentralized Identity Foundation (DIF) in March 2026, where the Trusted AI Agents Working Group released version 1.0.0 in July 2026 and calls it a ratified DIF standard. A TypeScript reference implementation (@kya-os/mcp) is published by DIF, and Vouched sells products built on it.

Each agent creates its own key and decentralized identifier (DID). On each call, the agent attaches a short-lived signature (at most 60 seconds) tied to the request, the server and a one-time nonce. Authority comes from a chain of signed delegation credentials rooted at a Responsible Party, with scoped actions and caveats such as spending limits, revocable through status lists. If authority is missing, the server can send the user to a consent page. The server signs its responses for audit. KYA-OS leaves the choice of which roots to trust to each server, and defines no contact channel, cross-server signalling or model identity; an older session-based profile with weaker guarantees remains valid in 1.x.

How it works

  1. Setup: the agent generates its own Ed25519 key pair and DID (did:key, or did:web published by its controller). The user or organisation that is accountable (the Responsible Party) signs a delegation credential naming the agent's key, with the allowed actions or scopes, caveats such as a maximum amount, an expiry and a revocation status entry; longer chains can re-delegate with narrower rights.
  2. The agent calls a tool on a KYA-OS server. In the per-request profile it attaches a proof object signed with its key, covering a hash of the request, the server's DID as audience, a nonce and a validity window of at most 60 seconds, and may carry its delegation chain in the request metadata.
  3. The server resolves the agent's DID document, checks that the key belongs to the DID, the audience, the request hash, the time window, that the nonce is new, and the signature.
  4. The server then verifies the delegation chain: each hop's signature, that each hop narrows its parent, that the last delegate is the key that signed the request, that the root is one it trusts (if configured), that the invoked action is allowed, and that no hop is revoked in its issuer's status list.
  5. If the delegation is missing or insufficient, the server returns a signed needs_authorization challenge with a consent URL; the user approves there, a new delegation credential is issued and the agent retries.
  6. If all checks pass, the server runs the tool and returns the result with a signed response proof binding the request and response hashes and the delegation used, which both sides can keep for audit.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
A server can allow or refuse each call by the agent's own key and by a scoped, attenuated delegation chain, including spending caveats, and can ask the user for consent when authority is missing. Which delegation roots it accepts is its own configuration.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Delegations can be revoked by the issuer, any ancestor or the Responsible Party, cascading to sub-delegations, and verifiers see it through status lists within about a minute for high-privilege scopes. There is no contact channel or way to warn other servers.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Each call can be traced to the agent's key, the delegation chain and its Responsible Party, and the server's signed response proofs and audit records bind what was requested and returned. The Responsible Party is a DID, linked to a verified person or organisation only if a KYC credential is attached.

Not addressed

  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No; registry and reputation only described (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Who is being identified?
IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Addressed
Yes. Each agent is identified by a DID it controls: did:key (derived from its public key) or did:web (a document its controller publishes). The agent must generate its own key pair, and no registry or verifier may generate or hold it. In the per-request profile the proof names the caller's DID and key id, and the key must be listed in that DID's document. A did:web may be a persistent, organisation-hosted identity.
Required by the specification · requirement level: MUST
Why this rating: The identifier names the agent itself, with a key each agent generates (unlike the provider-level identifiers of all three calibration examples).

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
Yes. In the per-request profile every call carries a proof object signed with the agent's DID key (EdDSA or ES256), covering a hash of the request method and parameters, the server's DID as audience, a nonce, and created and expires times; it is proof of possession, so a captured credential is useless without the key. An RFC 9421 HTTP signature can be added. The delegation credentials are signed by their issuers. A server that gates a call rejects it without a proof; the older session profile, still valid in 1.x, works differently.
Part of the normal flow · requirement level: MUST
Why this rating: A verifiable, proof-of-possession credential on every gated request (stronger than the calibration examples, which are also green).

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Addressed
Very short for the request proof: expires minus created must not exceed 60 seconds, checked with about 5 seconds of clock skew, and verifiers reject a longer window (ttl_too_long) or an expired one; the nonce must be unseen. Delegation credentials carry their own expiry set by the issuer with no maximum, and short-lived delegations are recommended for high-stakes resources. Legacy sessions expire after 30 minutes idle by default.
Required by the specification · requirement level: MUST
Why this rating: A specific short maximum that verifiers must enforce (same colour as Visa TAP's 8-minute window).

Authentication and authorization
Authentication of the agent or userDoes the receiving service itself authenticate the party making the request (the individual agent or the user)? Who exactly is authenticated, and by whom?Addressed
Yes, for the agent. Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Partly addressed
Partly. The Responsible Party at the root of the chain vouches for the agent by signing the delegation, and capability or KYC credentials from trusted issuers can add assurance. But which roots and issuers a server accepts is its own configuration: checking trusted roots applies only when configured, and trust-registry standing is advisory, not blocking. The protocol names no party that vets agents for all servers.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Addressed
Yes. Each delegation credential can carry a status list entry; the direct issuer, any ancestor or the Responsible Party can revoke it, and revocation cascades to every sub-delegation. Verifiers must fetch and verify the issuer's signed status list and reject revoked or unreadable entries; caches should be at most 60 seconds for high-privilege scopes, and the newer profile needs a live read for its top level. Access can be cut for one delegation, one agent key or a whole chain.
Part of the normal flow · requirement level: MUST
Why this rating: Revocation is defined in the protocol, fine-grained and reaches the verifier through status lists within a bounded cache time (all three calibration examples are red).

Notes

  • Name collisions: 'KYA' (Know Your Agent) is also used by unrelated work, e.g. the Open-KYA 'KYA Manifest Standard' (open-kya.github.io) and vendors' 'Know Your Agent' products. This analysis covers KYA-OS, formerly MCP-I, in the DIF repository decentralized-identity/kya-os-mcp. The spec also says it was 'previously known as MCP-Identity / MCP-I'.
  • Two profiles coexist in 1.x: a legacy session-bound profile (unsigned handshake, server-signed response proofs, StatusList2021 VC 1.1 delegations) and the per-request Entity Card profile (agent-signed proof on every call, VC 2.0 with ZCAP-LD). Ratings mostly follow the per-request profile, which SPEC.md section 5 calls the normative, durable authority; where the legacy profile is weaker, the answer says so.
  • Conformance has three separate ladders that reuse the names L1 to L3 (Core, Entity Card, Audit Assurance), which is easy to misread.
  • The specification uses RFC 2119 keywords. MAY* on the trust row reflects that trusted-root checking applies 'when the Verifier configures' it rather than a keyword.
  • The press release and Vouched page were checked with a web tool, which limits quotes to about 125 characters, so those quotes are sentence fragments. The DIF website and modelcontextprotocol-identity.io could not be fetched in this session; the GitHub repository was used as the primary source.
  • first_published 2025-05 refers to Vouched's first publication of MCP-I (May 2025), per its announcements; it is not cited in the rows.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (58 of 58 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
