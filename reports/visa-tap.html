Summary

Visa's Trusted Agent Protocol (TAP) helps online merchants tell AI shopping agents that Visa has approved apart from other bots. As agents begin to browse shops and pay on behalf of consumers, merchants need a way to let approved agents through while still blocking other automated traffic. TAP is a vendor specification published by Visa in October 2025, developed with Cloudflare, and available on the Visa Developer Center and GitHub under Visa's terms of use.

An approved agent provider signs each request to a merchant with HTTP Message Signatures (RFC 9421), the same building block as Web Bot Auth, and marks it as browsing or paying. The merchant, or a CDN in front of it, checks the signature against public keys that Visa publishes, a validity window of at most 8 minutes, and a one-time nonce. A request may also carry signed objects describing the consumer (an ID token with a stable identifier and obfuscated contact details) and the payment. TAP does not identify the individual agent, and leaves spending limits, purchase approval (handled by Visa Intelligent Commerce) and revocation outside the protocol.

How it works

  1. An agent provider is onboarded with Visa, and its public keys are published in Visa's key store at a well-known location.
  2. When the agent contacts a merchant, it signs the request with an HTTP Message Signature that includes created and expires times, a keyid, a nonce and a tag: agent-browser-auth for browsing or agent-payer-auth for paying.
  3. The request may also carry an Agentic Consumer Recognition Object (information about the consumer) and payment information in an Agentic Payment Container, each signed with the same key and linked by the same nonce.
  4. The merchant, or a site protection provider in front of it (e.g. a CDN), retrieves Visa's public key and checks the signature, the time window of at most 8 minutes and that the nonce has not been seen before. If any check does not pass, the message should be blocked.
  5. If the checks pass, the merchant treats the request as coming from an approved agent and can use the consumer information to recognise its customer. Payment approval and limits are handled by Visa outside TAP.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The merchant learns that the agent comes from a provider Visa has onboarded, and whether it is browsing or paying. Spending limits are enforced by Visa outside the protocol.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Visa can cut off a whole agent provider by removing its key, which reaches merchants as their caches refresh, and payments can be stopped in Visa's network. One specific agent cannot be cut off.

Accountability

Goal: an action can be traced back to the parties responsible for it.
An action can be traced to the agent provider, and to the consumer only when the consumer recognition object is sent.

Not addressed

  • Agent instance identifier: No (not addressed by the specification)
  • Authentication of the agent or user: No, only verifies the agent provider (not addressed by the specification)
  • Human approval: No, out of scope (handled outside the protocol)
  • Revocation: Not defined; Visa can remove keys (not addressed by the specification)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Addressed
Very short. A signature's created and expires times should be no more than 8 minutes apart and must fall around the current time, and merchants should block messages with a longer window. A nonce that has already been seen is also blocked, so each signature can only be used once. Keys themselves can expire, and messages signed with an expired key should be blocked.
Required by the specification · requirement level: SHOULD*
Why this rating: A specific short maximum that verifiers are told to enforce, even though the spec uses lowercase "should".

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (41 of 41 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
