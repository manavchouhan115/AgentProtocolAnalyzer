Summary

x402 lets a client, typically an AI agent or an app, pay for an API call, a web page or an MCP tool inside the request itself, using the long-unused HTTP status 402 Payment Required. It is aimed at services that want to charge per use without accounts, API keys or card checkouts. Coinbase created it in 2025; since 2026 it is governed by the x402 Foundation under the Linux Foundation, with about 40 member organisations. Protocol version 2 was released in December 2025 and Coinbase runs a hosted production facilitator; most payments use stablecoins on blockchains.

A server answers an unpaid request with its payment requirements (amount, asset, network, recipient, time limit). The client signs a payment authorization with its wallet key and retries with it in a header (or in MCP or A2A metadata). The server, usually through a facilitator service, checks the signature, balance, amount and validity window, runs the request and settles the payment on chain. x402 proves that someone with a funded wallet paid, not who the agent is or for whom it acts: identity comes only from optional extensions (wallet sign-in, HTTP Message Signatures or OAuth hints). It defines no scopes, human approval, revocation, contact channel or model identity.

How it works

  1. Setup: the resource server picks a facilitator (e.g. Coinbase's hosted one, or its own) and a recipient wallet; the client holds a wallet with funds on a supported network. No account or prior relationship between them is needed.
  2. The client (e.g. an AI agent) requests a resource. The server replies 402 Payment Required with a PAYMENT-REQUIRED header listing accepted payment options: scheme (e.g. exact), network, amount, asset, recipient (payTo) and maxTimeoutSeconds.
  3. The client chooses an option, signs a payment authorization with its wallet key (for exact on EVM: an EIP-3009 transfer authorization from its address to payTo, with a validity window and a random nonce) and retries the request with it in the PAYMENT-SIGNATURE header.
  4. The server sends the payload to the facilitator's /verify endpoint, which checks the signature recovers to the payer, the balance, the amount, recipient and validity window, and simulates the transfer.
  5. If valid, the server runs the request, then calls /settle; the facilitator submits the transfer on chain. The server returns the result with a PAYMENT-RESPONSE header carrying the transaction and the payer's address. (Some schemes settle before the request runs.)

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
A server can gate each resource behind a verified payment of a set amount, so access follows payment; it learns a payer wallet address but not the agent's identity, principal or permissions unless optional extensions are used.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
A server can refuse further payments from a wallet address, but anyone can create a new wallet; there is no revocation, contact channel or way to warn other servers.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Each paid request can be traced to a wallet address and an on-chain transaction, which is durable and public, but linking that wallet to an agent, operator or user requires information outside the core protocol.

Not addressed

  • Agent instance identifier: No (not addressed by the specification)
  • Acting for (authority): No (not addressed by the specification)
  • Human approval: No (not addressed by the specification)

  • Revocation: Not defined (not addressed by the specification)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Partly addressed
Partly. On a paid request the client sends a PaymentPayload: the chosen payment option plus a scheme-specific payment signed with its wallet key (for exact on EVM, an EIP-712 signature over an EIP-3009 transfer from the payer to payTo with a value, validity window and nonce). It proves control of funds and is single-use, but it does not sign the HTTP request itself, and unpaid requests carry nothing. A signature on every request exists only through the optional HTTP Message Signatures extension.
Required by the specification · requirement level: MUST*
Why this rating: A verifiable credential is defined only for requests that require payment, and it authorizes a transfer rather than authenticating the request.

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Partly addressed
Partly. Authorizations carry an explicit validity window (e.g. validAfter and validBefore on EVM), and the server's requirements state maxTimeoutSeconds, the maximum time for payment completion. The facilitator checks the window against the requirements, and each nonce can be used once on chain. Authentication and authorization
Authentication of the agent or userDoes the receiving service itself authenticate the party making the request (the individual agent or the user)? Who exactly is authenticated, and by whom?Partly addressed
No by default. Verifying a payment shows that the holder of a wallet key authorized a transfer, not who the agent or user is; the auth-hints extension itself says authentication and payment are parallel concerns. Optional extensions add authentication: sign-in-with-x lets the server verify a signed challenge proving control of a wallet address, and HTTP Message Signatures lets agents sign requests with a registered key (Web Bot Auth style, often a provider-level key).

Why this rating: The server can authenticate a wallet holder itself, but only through an optional extension; the core payment check is not authentication.

Notes

  • Name collision: 'x402' refers to this payment protocol; it is unrelated to the X.400/X.509 ITU-T standards naming. Version 1 and version 2 of x402 differ (e.g. v1 used X-PAYMENT headers); this analysis covers version 2.
