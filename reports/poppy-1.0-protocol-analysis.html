Summary

Personal Agent Protocol, known as Poppy, defines how a person's own AI agent (e.g. Meta's Muse) works with a company on that person's behalf: finding what the company offers, identifying itself, signing the person in, and using the company's APIs, website or company agent. It aims to replace today's all-or-nothing choice, in which agents either pass as the user or are blocked. Sierra leads the work with Meta and more than 100 design partners, and publishes it openly on GitHub under Apache 2.0, outside any standards body. Version 1.0 was published on 14 November 2026. Meta's Muse supports it, and Sierra says Shopify has enabled it for every merchant.

Every request carries a Session JWT, signed for that one request with a short-lived delegated key, that names the agent (its client_id, the URL of its metadata document), a pseudonymous User ID that differs at every company, and the Session. Account access is plain OAuth: the person signs in and approves scopes on the company's own page, and the agent then sends an access token alongside the Session JWT. Extensions add approval of an action's exact terms, a link to UCP for checkout, and a transitional sign-in with the user's password. Poppy does not identify individual agent instances or the AI model, defines no contact channel or warnings between companies, and leaves the choice of which agents to accept to each company.

How it works

  1. Setup: the Company publishes /.well-known/poppy.json listing its channels (APIs, website, Company Agent) and, if it offers sign-in, points to its OAuth issuer and scopes. The Personal Agent's operator publishes a client metadata document at an HTTPS URL, which is its client_id, with its public keys (jwks_uri).
  2. For each request, the Personal Agent signs a Session JWT with a short-lived delegated key, vouched for by a delegation signed with a key from its jwks_uri. The JWT names the Personal Agent, a pairwise User ID, the Session, the method and URL, and goes in the Poppy-Session header. A Web Bot Auth operator signature is recommended on top.
  3. The Company, or a gateway in front of it, fetches the client metadata and keys, verifies the delegation and signature, the audience, method, URL and freshness, and then starts or continues a signed-out Session for that pseudonymous User.
  4. When a task needs the User's account, the Personal Agent sends the User to the Company's own sign-in and consent page (Direct Sign-In, or Device Sign-In with a code). The User approves some or all of the requested scopes, and the Personal Agent exchanges the result for access and refresh tokens, authenticating with a client assertion.
  5. Signed-in requests carry the access token together with the Session JWT, whose ath claim binds the two. The Company checks the token, its scopes and that both belong to the same client_id, then decides. With the Operations extension, a consequential action first returns its exact terms, which the User, or the agent on the User's instruction, approves before the Company performs it.
  6. To end access, the Personal Agent revokes its refresh tokens (sign-out), or the User disconnects it in the Company's account settings; the Company can also refuse a client_id altogether.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
A Company can let accepted Personal Agents use signed-out APIs and pages, and gate account actions by OAuth scopes the User approves on its own page, with per-action approval of exact terms through the Operations extension. Which agents it accepts is its own policy, outside the protocol.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
The Company can revoke refresh tokens per account and Personal Agent, the User can disconnect an agent in account settings, and the Company can refuse a client_id, which cuts off every User of that Personal Agent. One agent instance cannot be cut off, and a delegated key stays usable until its delegation expires (up to 24 hours).

Accountability

Goal: an action can be traced back to the parties responsible for it.
Every verified request names the Personal Agent (client_id), a stable pseudonymous User, the Session and optionally an Agent ID, and signed-in requests name the Company's own account. Approvals can carry a reference to the operator's record, but the AI model and an operator contact are not identified.

Not addressed

  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Partly addressed
Short in practice, but the spec sets no fixed maximum for the per-request JWT. A Session JWT has no expiry; the Company must check that its signing time is within an acceptance window it chooses (the spec's example is one minute). The delegation that vouches for the signing key must expire within 24 hours, which verifiers check, and client assertions within 5 minutes. Access token lifetimes are left to the Company; the non-normative guides suggest hours, not days.
Required by the specification · requirement level: MUST
Why this rating: Verifiers must check freshness, but no specific short maximum is set for the per-request JWT (one minute is only an example), the enforced delegation limit is 24 hours, and access token lifetimes are unspecified; closer to MCP Authorization than to Visa TAP's fixed 8 minutes.

Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Partly addressed

Nobody vouches for the Personal Agent itself: its identity is a metadata document on its own domain, and which Personal Agents a Company accepts, and how, is outside the specification (the guides suggest allowlists or blocklists of client_id values). For signed-in requests, the Company's own issuer granted the token after the User approved scopes for that Personal Agent, the same basis as MCP Authorization. Signed-out requests rest only on the agent's own published keys.
Optional in the specification
Why this rating: The User's consent at the Company's issuer vouches for signed-in requests (as in MCP Authorization, green), but signed-out requests, where every Session starts, have no vouching party; the lower colour is chosen.
Evidence (3)
Accepting agents is outside the spec. Out of scope per Personal Agent Protocol, specification version 1.0, 4.1 Agent identity. (quote verified against the source)
“A Company decides which Personal Agents it accepts, and how it approves them is outside this specification.”
Guide suggestion for accepting agents. Source states Personal Agent Protocol 1.0, Guides (non-normative recommendations), Verifying personal agents. (quote verified against the source)
“Keep allowlists or blocklists of client_id values, and rate-limit session creation and new client_id values”
Signed-in access rests on the User's approval on the Company's page. Source states Personal Agent Protocol, specification version 1.0, 10.5 Signing in with the User's credentials. (quote verified against the source)
“Direct and Device Sign-In delegate access: the User approves scopes on the Company's own page, and the Company knows which Personal Agent acts”
Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Partly addressed
Partly. The issuer must publish a revocation endpoint, the Personal Agent signs out by revoking its refresh tokens there (RFC 7009), and the User can disconnect the Personal Agent in the Company's account settings, which revokes them too; the Company may also revoke a whole client_id. Access tokens already issued follow RFC 7009, so they can keep working until they expire unless the Company invalidates them. A delegated key cannot be withdrawn before its delegation expires (at most 24 hours), except by the operator removing the signing key.
Required by the specification · requirement level: MUST
Why this rating: The protocol defines revocation (required revocation endpoint, sign-out, disconnect), unlike the three calibration examples (red), but its effect on issued access tokens depends on the Company and delegations cannot be withdrawn early.
Evidence (6)
The revocation endpoint is required in the issuer metadata. Source states Personal Agent Protocol, specification version 1.0, 3.2 OAuth server. (quote verified against the source)
“revocation_endpoint revokes refresh tokens (4.6). Required.”
Users can disconnect an agent. Source states Personal Agent Protocol, specification version 1.0, 5.5 Ending Sessions and signing out. (quote verified against the source)
“The User can also disconnect the Personal Agent in the Company's account settings. That revokes its refresh tokens for the account.”
Companies may revoke a client_id. Source states Personal Agent Protocol, specification version 1.0, 5.4 Signing in. (quote verified against the source)
“MAY revoke a client_id that doesn't follow it (4.1).”
Effect on access tokens follows RFC 7009. Source states Personal Agent Protocol, specification version 1.0, 5.5 Ending Sessions and signing out. (quote verified against the source)
“What happens to access tokens issued under a revoked refresh token, including one that a new sign-in replaced (4.7), follows RFC 7009 §2.1”
Delegations cannot be withdrawn. Source states Personal Agent Protocol, specification version 1.0, 10.7 Delegated keys. (quote verified against the source)
“A delegation can't be withdrawn before it expires, so its lifetime limits what a stolen delegated key can do.”
The guides recommend invalidating access tokens at sign-out. Source states Personal Agent Protocol 1.0, Guides (non-normative recommendations), Token lifetimes and sign-out. (quote verified against the source)
“At sign-out, invalidate the access tokens issued under the revoked refresh token, as RFC 7009 §2.1 describes, or check on each request whether the authorization is still active”
Contact and escalationCan the service contact whoever is responsible for the agent (agent provider, user, model provider) if something goes wrong? Is a contact field required, optional or absent?Not addressed
No. Poppy defines no contact or escalation channel for the Personal Agent's operator: the client metadata has a name, logo, keys and redirect addresses but no contact field. In the Operations extension an approval can carry a reference to the agent's own record, so a Company and the operator can look into it later, but how to reach the operator is not defined. The feedback endpoint runs the other way, from agent to Company.
Not addressed by the specification
Why this rating: No contact field is required or defined (same as the three calibration examples).

No contact field or escalation channel is defined. Not found in Personal Agent Protocol, specification version 1.0, 4.1 Agent identity; 9. Task coverage; 10. Security considerations.
Approval references support later investigation with the operator. Source states Personal Agent Protocol 1.0, Operations extension (version 3), 6. Sending the approval. (quote verified against the source)
“so the Company and the Personal Agent's operator can look into the approval later.”
Feedback goes from agent to Company. Source states Personal Agent Protocol, specification version 1.0, 9.3 Feedback. (quote verified against the source)
“A Company can ask Personal Agents to tell it when a User's task can't be done through this protocol.”
Monitoring and provenance
Cross-party signallingCan one service warn others about a misbehaving agent (shared signals, reputation, abuse reports)?Not addressed
No. Poppy defines no way for one Company to warn others about a misbehaving Personal Agent. Pairwise User IDs and per-Company delegated keys are designed so Companies cannot match a User across Companies.
Not addressed by the specification
Why this rating: Not addressed (same as the three calibration examples).

“It is opaque and different for each Company, so Companies can't match Users with each other.”

Not addressed by the specification

Notes

  • The specification uses RFC 2119 keywords in capitals; requirement levels in this analysis follow those capitals.
  • Version 1.0 was announced by Sierra and Meta on 13 November 2026; the repository marked it published and froze it on 14 November 2026 (commit 8c02b42). Some third-party pages still call it 'draft 1.0', and the repository README still says the site publishes a draft specification; the 1.0 page itself says 'This is version 1.0.'
  • Venue is set to 'vendor': the specification is written in a repository run by Sierra, with Meta and design partners contributing feedback, and no standards body or foundation governs it.
  • The guides are non-normative recommendations; claims quoted from them are marked as guidance in the answers.
  • The repository contains AGENTS.md files with instructions aimed at AI coding tools (for contributors editing the site). They were treated as data and not followed.
  • Name collision: 'PAP' is also the PPP Password Authentication Protocol (RFC 1334), which is unrelated. poppy.md is an unofficial third-party site and was not used as a source.
  • Quotes from sierra.ai, muse.ai and about.fb.com were checked with a web tool (WEB-OK) because those sites could not be downloaded by script from this environment.

Open questions

  • Shopify's enablement for every merchant is stated by Sierra; no Shopify documentation was found that says what Shopify's poppy.json files offer (signed-out Sessions only, sign-in, UCP extension).
  • How many Companies actually verify the Session header (a SHOULD) rather than ignoring it, and how short their acceptance windows are.
  • Whether Muse sends an Agent ID, and whether it uses blind signing or holds delegated keys on Meta's servers.
  • Whether Companies invalidate access tokens at sign-out in practice, which decides how quickly revocation takes effect.
  • The spec says the Company is identified by its domain; it does not say how a Personal Agent operator's keys used for Web Bot Auth relate to its client_id beyond 'a shared origin alone does not establish' the link.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (75 of 75 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
