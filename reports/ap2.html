Summary

The Agent Payments Protocol (AP2) gives merchants and payment providers cryptographic proof that a user really approved a purchase made by an AI shopping agent. Because an AI agent can be manipulated (e.g. by prompt injection), AP2 treats every agent as a potential attacker and asks for a signed, user-approved mandate before a checkout is completed or a payment credential is released. It sits on top of a commerce protocol such as Google's Universal Commerce Protocol (UCP) or A2A. Google published AP2 in September 2025 and released v0.2 in April 2026, when it donated the protocol to the FIDO Alliance; the version number is pre-1.0 and standardisation continues there.

The shopping agent prepares a Checkout Mandate (what is bought, bound to a merchant-signed checkout) and a Payment Mandate (how it is paid). A Trusted Surface, a non-AI interface such as a wallet, shows them to the user and has them signed, either with the user's own digital credential or with the agent provider's key. If the user is present, they approve the exact checkout; if not, they approve limits (merchants, items, amounts, budget, dates) and the agent signs the final mandate with its own key. Merchants and payment providers verify signatures and limits and return signed receipts that serve as dispute evidence. AP2 leaves agent identification, revocation, contact and model identity to other layers.

How it works

  1. Setup: the verifiers (merchant, credential provider, payment processor) decide whom they trust to vouch for user approval: issuers of user credentials (e.g. a wallet or bank) or a list of trusted agent providers.
  2. The shopping agent builds a checkout with the merchant through a commerce protocol (e.g. UCP); the merchant returns a merchant-signed Checkout JWT.
  3. The agent prepares Checkout and Payment Mandate content and sends it to a Trusted Surface, which shows it to the user and obtains consent. The result is a signed SD-JWT mandate: a closed mandate for the exact checkout (user present) or an open mandate with limits and the agent's public key (user not present).
  4. In the autonomous case, the agent later signs a closed mandate for a specific checkout with its own key and presents it together with the open mandate, disclosing only the parts that are needed.
  5. The credential provider verifies the Payment Mandate before releasing a payment credential; the merchant verifies the Checkout Mandate (signature chain, checkout hash, limits) before completing the checkout. Each verifier returns a signed receipt, and the mandates and receipts together form dispute evidence.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The merchant and payment providers act only on a user-approved mandate: the exact checkout when the user is present, or one that fits enforced limits (merchants, items, amounts, budget, dates) when not.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
AP2 defines no revocation; payment-side parties may reject overlapping mandates or invalidate payment tokens, and expiry limits open mandates, but a verifier cannot be told to stop accepting a mandate or agent key.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Signed mandates and receipts give a non-repudiable record of what the user approved and what each party saw, tied to a user credential or agent provider and, in autonomous mode, to the agent's key; not to a named agent or model.

Not addressed

  • Revocation: Not defined (not addressed by the specification)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No; receipts are per transaction (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Who is being identified?
IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Partly addressed
Partly, and only in some modes. AP2 defines no agent name or ID; it leaves agent identification to the commerce protocol. When the user is not present, the open mandate must carry the agent's public key (cnf claim), so the verifier learns the key the user authorised. In the Trusted Agent Provider model, the mandate is signed by the agent provider, whose issuer value (iss) names it. In the user-present User Credential model, nothing identifies the agent.
Optional in the specification · requirement level: MUST
Why this rating: An agent key (MUST, but only in the autonomous mode) or the agent provider is identified only in some modes, and agent identification is otherwise left to the commerce protocol (Visa TAP is yellow for a provider key on every request).

Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Partly addressed

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
A user credential issuer or a trusted agent provider. In the User Credential model, the verifier trusts the issuer of the user's credential (e.g. a wallet or bank) to guarantee that mandates are signed only after consent; in the Trusted Agent Provider model, it trusts the agent provider directly, which requires a trust relationship with each provider. The user's mandate then vouches for the agent's key. Whether an agent itself is trustworthy is left to the commerce protocol.
Required by the specification · requirement level: MUST
Why this rating: The protocol names the vouching parties and only mandates they back are accepted (same as Visa TAP and MCP Authorization), although which issuers or providers to trust is each verifier's choice.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Not addressed
Not defined. AP2 has no way to revoke a mandate or an agent key that reaches merchants or payment providers. Receipts narrow what an open mandate can still be used for, credential providers, networks and payment processors may reject overlapping mandates or invalidate payment tokens they issued, and the shopping agent should let users manage active mandates; managing mandates held by an external Trusted Surface is out of scope.
Not addressed by the specification

Notes

  • The receiving service is taken to be the merchant (which verifies the Checkout Mandate); rows mention the credential provider and payment processor where they are the verifier.
  • AP2 v0.2 replaced the v0.1 Intent and Cart Mandates with Checkout and Payment Mandates; descriptions of v0.1 elsewhere do not apply.
  • The repository is still under google-agentic-commerce, while Google states that standardisation continues in the FIDO Alliance; venue is recorded as vendor for this version.
  • AP2 uses RFC 2119-style keywords but does not cite RFC 2119; requirement levels are taken as written.

Open questions

  • The specification requires vct values with a version suffix (e.g. mandate.checkout.1), but the v0.2.0 JSON schemas say the value MUST be 'mandate.checkout' and 'mandate.payment'. Which is authoritative?
  • Is the agent key in open mandates expected to be per agent instance, per task or per agent product? The answer decides whether it works as an instance identifier.
  • Verification relies on Delegate SD-JWT, an individual draft hosted on GitHub. Will FIDO adopt or replace it?
  • How should verifiers learn which user credential issuers and agent providers to trust? No trust list format or distribution is defined.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (63 of 63 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
