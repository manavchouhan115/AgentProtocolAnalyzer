Summary

The Trust Spanning Protocol (TSP) is a general-purpose messaging layer from the Trust over IP Foundation, part of LF Decentralized Trust. It lets two parties that identify themselves with different kinds of verifiable identifiers (e.g. DIDs) exchange messages that are always authentic and, if wanted, confidential and private, much as IP connects different networks. Version 1.0 was approved by the Technology Stack Working Group on 30 October 2026. A separate ToIP draft, TSP-Enabled AI Agent Protocols, applies it to AI agents: TMCP runs MCP over TSP and TA2A runs A2A over TSP. That draft is incomplete, and TMCP exists mainly as an OpenWallet Foundation implementation.

Every TSP message names the sender's and receiver's identifiers (VIDs) and is signed with the sender's key, optionally encrypted to the receiver; the receiver resolves and appraises the sender's VID against its own policy before relying on it. TMCP wraps each MCP message in a TSP message over the normal MCP transport, and the draft makes each agent its own TSP endpoint, with authority delegated by signed credentials that can only narrow, must be revocable and must trace back to a person or organisation. TSP itself leaves out authorization, message freshness and trust decisions; the agent draft does not yet define the MCP binding, model identity, contact channels or warnings between services.

How it works

  1. Setup: each agent or service (a TSP endpoint) controls one or more verifiable identifiers (VIDs), e.g. a did:webvh whose key history is published and supports key rotation. In the TMCP implementation, the MCP client and server each get their own DID.
  2. Introduction: the client learns the server's VID out of band and sends a relationship-forming message (TSP_RFI). The server resolves the client's VID, verifies and appraises it against its own policy, and replies with TSP_RFA if it accepts.
  3. Each message, e.g. an MCP JSON-RPC request in TMCP, is placed in a TSP message naming both VIDs, optionally encrypted to the receiver, and signed with the sender's key. It travels over the usual transport (Streamable HTTP, SSE, WebSockets) or through intermediaries.
  4. The receiving endpoint checks that the relationship exists, verifies the signature against the sender's current key state, decrypts, checks that the sender VID inside matches, and passes the content up; anything that does not verify is silently dropped.
  5. Under the draft agent companion, an agent exercising authority presents a chain of authorization credentials (ACDCs) from its principal. The receiver checks at that moment that every credential in the chain is valid and unrevoked and roots in an issuer it trusts, and computes the narrowed effective authority.
  6. Afterwards, either side can cancel the relationship (TSP_RFD), a principal can revoke a delegation in its status registry, and a compromised key is rotated through the VID type.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
Core TSP lets a service accept or drop messages per sender VID and relationship, by its own policy. The draft adds delegation credentials whose narrowing authority a service can enforce, but the MCP binding that would map them to tool calls is not yet written.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
A service can cancel or block a relationship with one VID, which is one agent where each agent is its own endpoint. The draft adds per-delegation revocation checked at each use; key compromise is handled by VID rotation, which reaches each peer when it re-resolves.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Every message is signed and binds both sender and receiver VIDs, so the sender cannot disown it. The draft requires every authority to trace back to a natural person or organisation; the AI model and a contact are not identified.

Not addressed

  • Credential lifetime: None for messages; left to higher layers (explicitly out of scope)
  • Human approval: No (delegation is issued, not approved) (not addressed by the specification)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
A signature by the sender over every TSP message (envelope and payload), made with the key bound to the sender's VID, so it is proof of possession and covers the whole content. The payload can also be encrypted to the receiver, with the sender's VID inside. The signature binds the receiver's VID too, so a message cannot be redirected or disowned. In TMCP every MCP request, response and streamed event over Streamable HTTP is sealed this way.
Required by the specification · requirement level: MUST
Why this rating: A verifiable credential (signature) on every message (same as Web Bot Auth and Visa TAP, and stronger in that it covers the whole content).

TSP cannot create trust. Source states Trust Spanning Protocol (TSP) Specification, Release 1.0, Verifiable Identifiers. (quote verified against the source)
“While TSP aids in transmitting trust signals between endpoints, it cannot instantiate trust where none exists.”
Appraisal by the receiver. Source states Trust Spanning Protocol (TSP) Specification, Release 1.0, VID General Requirements. (quote verified against the source)
“Appraisal is the assessing endpoint’s evaluation of the records a VID type publishes, such as its inception record and its rotation and pre-rotation events”
Credential chains root in issuers the verifier trusts. Source states ToIP AIM WG, TSP-Enabled AI Agent Protocols (v1.0 Draft), Delegation of Authorization and Duty. (quote verified against the source)
“A verifier MUST accept a root issuance only when it roots trust in that Issuer for the resource in question.”
Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Partly addressed
Partly, in the draft. Each delegated authority must be revocable through its credential status registry, and the verifier must check at the time of use that every credential in the chain is still valid, so revoking one hop takes effect at the next check and can target one agent. Core TSP defines no revocation: a relationship can be cancelled with an optional TSP_RFD message, and a compromised key is rotated through the VID type, which reaches each peer only when it re-resolves.
Only in an extension or companion specification · requirement level: MUST
Why this rating: Prompt, per-delegation revocation is defined only in the draft companion; core TSP offers relationship cancellation and key rotation, which are not revocation.
Evidence (4)
Delegations must be revocable. Source states ToIP AIM WG, TSP-Enabled AI Agent Protocols (v1.0 Draft), Delegation of Authorization and Duty. (quote verified against the source)
“A delegated authority MUST carry a validUntil validity bound and MUST be revocable through its credential status registry.”
Status is checked at the time of use. Source states ToIP AIM WG, TSP-Enabled AI Agent Protocols (v1.0 Draft), Delegation of Authorization and Duty. (quote verified against the source)
“Verification of a delegated authority MUST confirm, at the time of exercise, that every ACDC on the relevant chain”
Relationship cancellation is optional. Source states Trust Spanning Protocol (TSP) Specification, Release 1.0, Relationship Forming Decline or Cancel. (quote verified against the source)
“While sending explicit messages to cancel a relationship is not strictly necessary in TSP, such messages MAY be beneficial for upper-layer protocols that require a clear and definite termination of relationships.”
Key recovery reaches peers one by one. Source states Trust Spanning Protocol (TSP) Specification, Release 1.0, Key Compromise and Recovery. (quote verified against the source)
“Recovery is not global: it takes effect with respect to each peer independently, when that peer obtains the new key state.”
Contact and escalationCan the service contact whoever is responsible for the agent (agent provider, user, model provider) if something goes wrong? Is a contact field required, optional or absent?Not addressed
No. Neither TSP nor the agent draft defines a contact or escalation channel. A TSP relationship is itself a channel to the agent's endpoint, and the draft's accountability chain names the responsible principal by identifier, but how to reach that principal about an incident is not defined.
Not addressed by the specification
Why this rating: No contact field or escalation channel is defined (same as the three calibration examples).

Monitoring and provenance
Cross-party signallingCan one service warn others about a misbehaving agent (shared signals, reputation, abuse reports)?Not addressed
No. TSP carries trust signals between the two endpoints of a relationship, but defines no way for one service to warn others about a misbehaving agent. Its privacy design (non-correlatable VIDs, nesting, routing) works against linking an agent across services.
Not addressed by the specification

Notes

  • Both specifications use RFC 2119 keywords in capitals; requirement levels in this analysis follow them.
  • This analysis covers two documents. Rows rated from the TSP-Enabled AI Agent Protocols draft are marked coverage 'extension', because that draft is a separate, incomplete companion: its MCP over TSP, TEA Signed Payload and Security and Trust Considerations sections are TODO, and it has no A2A section.
  • The companion draft's GitHub repository showed no commits from this environment, so it was read only on its published GitHub Pages page; all quotes from it, and from the OWF book and LF Decentralized Trust blog, were checked with a web tool (WEB-OK).
  • TSP 1.0 was approved by the Technology Stack Working Group on 30 October 2026; the specification's foreword still has a placeholder for the Steering Committee approval date.
  • TMCP is described from the OpenWallet Foundation implementation (a transport hook on a fork of the MCP Python SDK). No public TA2A specification text or code was found; TA2A appears only in presentations and as a goal of the draft.
  • The rubric assumes a service receiving requests. TSP is a peer-to-peer messaging layer, so 'receiving service' is read as the receiving TSP endpoint (e.g. a TMCP server).
  • Venue is set to 'foundation' (Trust over IP, part of LF Decentralized Trust); the TSP specification is published under the OWF Contributor License and OWFa 1.0.
  • Name collision: an unrelated 'Trust Standard Protocol' (LexiTSP) for AI provenance also uses the abbreviation TSP. It was not used.

Open questions

  • Will the agent draft be updated to reference TSP 1.0 instead of TSP Rev 2, and do any of its requirements depend on Rev 2 behaviour?
  • How does TMCP interact with MCP's own OAuth-based authorization: does TSP replace it, or run underneath it? The draft's MCP binding is not written yet.
  • Is there any TA2A specification or implementation beyond presentation slides?
  • In practice, do deployments give each agent its own VID (as the draft intends) or share one VID across a provider's agents? This decides the identifier, instance and authentication ratings.
  • Who runs the credential status registries for delegation ACDCs, and how quickly do verifiers see a revocation?

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (61 of 61 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
