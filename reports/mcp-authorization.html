Summary

MCP Authorization is the security layer of the Model Context Protocol (MCP), an open protocol that lets AI applications connect to outside tools and data through MCP servers. It answers one question for a remote MCP server: is this application allowed to call me on behalf of this user, and for what? Authorization is optional in MCP and covers only servers reached over HTTP, not local servers. The current version is the dated revision 2026-07-28, maintained by the MCP project, and it is supported by AI applications such as Claude's connectors.

It is a profile of OAuth 2.1, the widely used standard for delegated access on the web. The MCP server names its authorization server; the AI application sends the user there to sign in and approve access, and receives an access token that only works at that one server and only for the approved scopes (permissions). The token is sent with every request and the server checks it. The server therefore learns that the request is approved, but not which agent instance or AI model is behind it. MCP itself defines no way to revoke access or to contact the application's operator, and the token is a bearer token, so whoever holds it can use it.

How it works

  1. The AI application (the MCP client) calls the MCP server without a token and receives a 401 response that points to the server's protected resource metadata (RFC 9728).
  2. From that metadata the client finds the server's authorization server and identifies itself with a client ID, ideally an HTTPS URL to a Client ID Metadata Document describing the application.
  3. The client opens the authorization server in the user's browser. The user signs in and approves the requested scopes; PKCE protects this exchange.
  4. The authorization server issues an access token for that specific MCP server (using a resource indicator, RFC 8707).
  5. The client sends the token as a bearer token on every request. The MCP server checks that it is valid, unexpired and issued for it, and answers 401 (invalid token) or 403 (missing scope) otherwise.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The server receives a grant the user approved, limited by scopes and bound to that server, and can ask for more scopes through step-up authorization.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Access can be cut off at the authorization server, per user or per client: at once for opaque tokens checked with the authorization server, and only at expiry for self-contained tokens. There is no way to cut off one specific agent instance.

Accountability

Goal: an action can be traced back to the parties responsible for it.
An action can be traced to the client application, and to the user only if the authorization server exposes the user to the server.

Not addressed

  • Agent instance identifier: No (not addressed by the specification)
  • Acting for (authority): No by default (not addressed by the specification)
  • Authentication of the agent or user: No, only checks the token (handled outside the protocol)
  • Revocation: Not defined by MCP (handled outside the protocol)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
An OAuth access token, sent as a bearer token in the Authorization header of every HTTP request. It is issued by the server's authorization server for that specific MCP server, and can be a signed JWT or an opaque string, as the authorization server decides. A bearer token is not bound to the client, so anyone who obtains it can use it. Proof-of-possession binding (e.g. DPoP or mTLS) is not part of the specification.
Required by the specification · requirement level: MUST
Why this rating: A defined credential on every request that the server can verify. The answer notes it is a bearer token, not proof of possession.

No. The MCP server does not authenticate the agent or the user itself. The user signs in at the authorization server, which then issues a token; the MCP server only checks that the token is valid and was issued for it. Scoped authorizationDoes the protocol tell the service what the agent is allowed to do (scopes, per-action limits)? How fine-grained is it?Addressed
Yes. Access is limited by OAuth scopes (named permissions) that the user approves at the authorization server, and the MCP server can say which scopes it needs. If a token lacks a needed scope, the server answers 403 with insufficient_scope, and the client can ask the user for more access (step-up authorization). Scopes are defined by each server; MCP defines no per-action limits such as amounts.
Part of the normal flow · requirement level: SHOULD
Why this rating: Scoped permissions are part of the normal flow and enforced by the server.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Not addressed
Not defined by MCP. The authorization server can revoke tokens under OAuth Token Revocation (RFC 7009), but how fast this reaches the MCP server depends on the token type. If the server checks each opaque token with the authorization server, a revoked token stops working at once; a self-contained token such as a JWT is checked by the server on its own, so it keeps working until it expires. Access can be cut off per user or client, not per agent instance.
Handled outside the protocol
Why this rating: MCP does not define revocation; RFC 7009 at the authorization server is outside the protocol (same as Web Bot Auth and TAP).

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (46 of 46 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
