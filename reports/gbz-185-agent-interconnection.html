Summary

GB/Z 185 is a Chinese national guidance document series, 'Artificial intelligence, Agent interconnection', meant to give agents from different vendors a common way to identify each other, describe themselves, find each other, interact and call tools. This analysis covers Part 2 (identity code) and Part 3 (identity management), using Part 1 (architecture) as context. All three were published by SAMR and SAC on 22 May 2026 under the national IT standards committee (SAC/TC 28), drafted by CESI, BUPT and dozens of companies. They are guidance technical documents (GB/Z), not mandatory or recommended national standards. News reports say the first identity-code nodes were issued in July 2026.

A registration service provider checks an agent's evidence and assigns it an identity code. The code is a hierarchical OID under 1.2.156.3088 that names the registration service provider, the registering organisation or person, the agent program and, optionally, one running instance. A credential issuer then gives the agent a signed credential, typically a public-key certificate for a key the agent holds. When the agent contacts another agent or a tool, the relying party asks it for a signed proof, ideally over a fresh challenge. Either the relying party or a separate identity verifier checks that proof against the certificate chain, whose roots must come from nationally recognised certification bodies. Credentials can be locked or cancelled, and verifiers can query their status. Scopes, delegation details, lifetimes, transport bindings and data formats are left open or only recommended.

How it works

  1. An agent delegator (a person or an organisation) authorises an agent and asks a registration service provider to register it. The request includes registration information such as the agent's functions, supported tasks and version.
  2. The registration service provider assesses risk and checks evidence (e.g. code or model hashes, delegation records, behaviour boundaries). It then creates an identity account and assigns an identity code, which may follow Part 2's OID structure, e.g. 1.2.156.3088.1.1.34C2.478BDF.3GF546.
  3. In the example flow, the agent generates its own key pair in an HSM or TEE. A credential issuer (the registration service provider or a third party) issues a public-key certificate that binds the key to the identity code and other attributes.
  4. When the agent asks another agent or a tool provider (the relying party) for a service, the relying party picks an authentication policy. It can get a fresh random challenge from an identity verifier.
  5. The agent signs a 'process credential package' with its private key, including the challenge, and submits it. The relying party verifies it itself or forwards it to the identity verifier.
  6. The verifier checks the signature and certificate chain up to a nationally recognised root. It may also check validity period, lock or cancellation status, audience, scope and delegation chain, then returns a signed assertion with the result.
  7. The relying party combines the assertion with its own authorization policy, decides, and if it allows the request sets up an authenticated, secure session with the agent.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The relying party learns which registered agent it is talking to and can check a proof tied to that agent's own key, then applies its own policy. Scopes are only optional, undefined fields, so permission control is mostly left to each service.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
A specific agent's account or credential can be locked or cancelled, and verifiers can query that status, which is finer than provider-level key removal. Whether a revoked credential is refused depends on the verifier checking status, which is only recommended. There is no route for a service to report an agent.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Each code names the registration service provider and the registering organisation or person, the delegator bears final responsibility by definition, and registries must keep audit-protected logs and archive records after cancellation. A service still needs the registry's cooperation to turn a code into a named party.

Not addressed

  • Contact and escalation: No channel for the relying party (not addressed by the specification)
  • Cross-party signalling: None (not addressed by the specification)

Who is being identified?
IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Addressed
Yes, per agent. The identity code is an OID string with five parts: the 1.2.156.3088 prefix, a version, the registration service provider, the registration requester (the organisation or person that registered the agent), and a custom serial that names the agent program and optionally an instance. Part 2 says one code maps to only one agent, so it is not shared across a provider's agents the way a provider key is. Part of the normal flow · requirement level: MUST*

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Partly addressed
Partly. The agent credential is a tamper-proof data set issued by the credential issuer; in the informative example it is a public-key certificate for a key only the agent holds. At authentication the agent builds a 'process credential package', which in the example is signed with its private key over a verifier-supplied random value, so it is proof of possession. The credential is presented when the relying party triggers authentication, after which a session is set up; it is not required on every request. The package format and what it must cover are not specified, and the dynamic challenge is only recommended.
Part of the normal flow · requirement level: SHOULD
Why this rating: A verifiable credential is defined, but it is presented at session setup rather than on every request and its format and freshness binding are only recommended or informative (the calibration examples are green because they carry a credential on each request).

Notes

  • The official text is only available as page images in SAMR's openstd online viewer (no text layer, anti-copy measures). Pages were reconstructed from the viewer's image tiles in a browser, captured as screenshots, and OCR'd (RapidOCR) into text snapshots. Every quoted passage was compared by eye with the page image, and OCR errors in quoted passages were corrected in the snapshot before running the quote checker. Treat quotes as transcriptions of the official images.
  • Requirement levels: the documents follow GB/T 1.1-2020 verb forms, where 应 = shall (mapped to MUST), 宜 = should (SHOULD), 可 = may (MAY). They do not use RFC 2119 keywords, but GB/T 1.1 gives these words the same formal role, so no asterisk is used for them. MUST* in the identifier row marks the phrase 只能 ('can only'), which is not one of the formal provision verbs (lowercase-style requirement).
  • GB/Z documents are national standardization guidance technical documents; even 应 (shall) provisions are guidance for those who choose to follow the document, not legal obligations.
  • Part 3 says identity codes 'may' be allocated according to Part 2, so the OID code structure is optional when following Part 3 alone.
  • Several rows depend on informative annexes (Part 2 Annexes A to C, Part 3 Annexes A to C), which are examples, not requirements. The answers say where this is the case.
  • Parts 4 to 7 (description, discovery, interaction, tool calling) may add relevant mechanisms (e.g. mutual authentication in interaction and authorization in tool calling) and were not analysed.
  • News coverage gives conflicting dates (Xinhua says the series was released in June 2026). The SAMR records and covers show 2026-05-22.

Open questions

  • Part 3 says a verifier must treat a locked credential as invalid (8.4 c), but checking status is only recommended (9.2 b 2) and a preset policy may accept when status is unavailable. Which takes precedence in practice?
  • No wire format is given for the agent credential, the process credential package or the identity assessment assertion. Do Parts 6 and 7, or the national rules on agent public-key certificates referred to in 9.2, define them?
  • Which body is the 'competent authority' (主管部门) that allocates registration service provider codes and recognises foreign registries? The documents do not name it.
  • How should a relying party resolve an identity code (registry, requester) into a named, contactable organisation? No resolution service is described in Parts 1 to 3.
  • Is there a primary, deployer-published list of registration service providers or identity-code nodes issued in July 2026?

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted.
