Summary

AAuth is a proposed protocol that gives every AI agent its own cryptographic identity and lets it act for a person across organisations without being registered in advance at each service. It starts from the view that OAuth client IDs and API keys do not fit agents, which discover services at run time and work on long tasks across many organisations. It was written by Dick Hardt (Hellō) as an individual IETF draft, currently at revision -11 (September 2026). In November 2026 an OpenID Foundation working group was created to take it forward. Implementations so far are exploratory.

Each agent gets an identifier and an agent token from its agent provider and signs every request with its own key, so no token works without that key. On top of this, resources choose one of five access modes: recognising the agent alone, running their own sign-in, or relying on a person server that the person chooses. The person server tells the resource who the agent acts for (as a per-resource pseudonym), collects consent, and issues scoped auth tokens, optionally through the resource's own access server. It also supports missions, permission requests and audit records for governing agents, and a revocation cascade. AAuth does not define model identity, a contact channel or a trust registry, and in the person-based modes the resource does not see which agent it is talking to.

How it works

  1. The agent creates a key pair and proves itself to its agent provider, which issues an agent token with the agent's identifier (aauth:local@domain) and public key.
  2. The agent calls a resource with an HTTP Message Signature over the request and its agent token in the Signature-Key header. The resource checks the signature and the token, and may decide on the agent's identity alone.
  3. If the resource needs to know the person, it asks for a person token. The agent gets one from its person server, which identifies the person to that resource with a pseudonymous identifier.
  4. If the resource needs authorization, it returns a resource token describing the access it offers. The agent takes this to its person server, which collects the person's consent if needed (and, for four-party access, asks the resource's access server) and returns a scoped auth token.
  5. The agent presents the auth token on its signed requests, and the resource enforces the scopes. Tokens last at most an hour and can be revoked through a cascade that starts at the agent provider or person server.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
Strong when a person server is used: the resource gets scoped, person-approved auth tokens bound to the agent's key. In agent-identity mode the resource decides on who the agent is, with no scopes.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Access can be cut off per agent through the revocation cascade, and tokens expire within an hour. An agent token presented directly to a resource cannot be revoked and lasts up to 24 hours, and servers without a revocation endpoint keep honouring tokens until they expire.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Each agent is bound to exactly one person at the person server, which can keep a mission log and audit records. Resources see a per-resource pseudonym for the person, and the specific agent only in the two simplest modes.

Not addressed

  • Status and adoption: Early draft, now at the OpenID Foundation ()
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (extension point only) (not addressed by the specification)

Who is being identified?
IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Addressed
Yes. The agent provider gives each agent its own identifier of the form aauth:local@domain, where the domain is the provider's. It names a specific agent with its own signing key, not just the application, and stays the same when the key rotates. The resource sees this identifier only in the two simplest access modes; in the person-based modes it is deliberately hidden (see the next row).
Required by the specification · requirement level: MUST
Why this rating: The identifier names the individual agent, unlike the client or provider identifiers of MCP Authorization, Web Bot Auth and Visa TAP.

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
An HTTP Message Signature (RFC 9421) on every request, covering the method, host, path and the Signature-Key header (plus a digest of the body for server endpoints). The request also carries a JWT: the agent token, a person token or an auth token, each containing the agent's public key. The verifier checks that this key signed the request, so every token is proof of possession and useless without the private key.
Required by the specification · requirement level: MUST
Why this rating: A signed credential on every request, with proof of possession (stronger than MCP Authorization's bearer token).

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Addressed
Very short for signatures, short for tokens. Servers reject a signature created more than 60 seconds ago by default. Person and auth tokens MUST NOT last more than 1 hour; agent tokens SHOULD NOT last more than 24 hours. There is no nonce, so the same signed request could be replayed within the 60-second window unless the server keeps an optional replay cache.
Required by the specification · requirement level: MUST
Why this rating: A specific short window that verifiers enforce (same as Visa TAP).

Yes. The server verifies the HTTP signature and its 60-second window, verifies the presented JWT with the issuer's keys (found through the issuer's well-known metadata), checks that the token has not expired, and checks that the key inside the token is the one that signed the request. Authentication and authorization
Authentication of the agent or userDoes the receiving service itself authenticate the party making the request (the individual agent or the user)? Who exactly is authenticated, and by whom?Addressed
Yes for the agent. Every request is signed with a key that belongs to that specific agent instance, and the token presented binds that key, so the resource verifies the actual sender rather than a provider-wide key or a bearer token. The user is authenticated by the person server, not by the resource: a person token gives a stable pseudonym and makes no claim about how the person's identity was checked.
Required by the specification · requirement level: MUST
Why this rating: The resource verifies per-agent proof on every request, unlike the provider-level keys of Web Bot Auth and Visa TAP.

Scoped authorizationDoes the protocol tell the service what the agent is allowed to do (scopes, per-action limits)? How fine-grained is it?Addressed
Yes. In the person-server modes the agent receives an auth token with scopes the resource defined and the person approved, and the granted scope can never be broader than what the resource offered. Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Partly addressed
Partly. Revocation is defined: servers SHOULD publish a revocation endpoint, and an agent provider revoking an agent token triggers a cascade through the person server to the person tokens and auth tokens issued to that agent, at agent level rather than provider level. Gaps: an agent token presented directly to a resource has no revocation path (up to 24 hours), and a server without a revocation endpoint keeps honouring tokens until they expire.
Optional in the specification · requirement level: SHOULD
Why this rating: Revocation is defined and can target one agent, but it does not reach every verifier.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (71 of 71 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
