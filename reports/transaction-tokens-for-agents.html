Summary

Inside a company's systems, one request often passes through many internal services, and when an AI agent started it, the services deep in that chain usually cannot tell. OAuth Transaction Tokens, an IETF OAuth working-group draft, already give each internal service a short-lived signed token describing who the transaction is for and what it is for. Transaction Tokens For Agents is an individual draft by Ashay Raut (version -03, October 2026) that adds agent context to those tokens, so internal services can tell agent-driven calls from direct human calls and audit them. No deployment is named.

A single Transaction Token Service in the trust domain issues the tokens. The extension adds an agentic_ctx claim naming the agent that started the chain and the agent at the current hop, a hop count, and an optional minimum assurance level, and fixes how the user (sub) and the delegated agent (act) are carried. Each time an agent hands work on, it gets a replacement token: identity stays fixed, the hop count rises and permissions can only shrink. The tokens are bearer-style and stay inside one trust domain. Neither draft defines revocation, contact channels, model identity or a way for services to warn each other.

How it works

  1. A user asks an agent to do a task (or the agent starts on a schedule). The agent obtains an ordinary OAuth access token, through an authorization code flow for a user or client credentials when autonomous, and calls the trust domain's external endpoint (e.g. an API gateway).
  2. The gateway sends that access token and its own credentials to the Transaction Token Service in an OAuth token-exchange request, asking for a Transaction Token with a narrow scope for this transaction.
  3. The Transaction Token Service authenticates the gateway, validates the access token, checks (e.g. by looking up the client_id in an Agent Attribute Store) whether the caller is an agent, and issues a short-lived signed token: sub (the user, or the agent itself), act copied from the access token, scope, a transaction ID (txn) and agentic_ctx (proximate and originating agent, hop count 1).
  4. Each internal service receives the token in the Txn-Token HTTP header, checks its signature, trust-domain audience and expiry, and applies its own policy (e.g. restrict agent chains, or refuse beyond a hop limit).
  5. When an internal agent takes over and calls further services, it asks for a replacement token: sub, act, txn and the originating agent stay fixed, the proximate agent changes, the hop count rises, and scope and assurance level can only go down.
  6. The Transaction Token Service logs each issuance and replacement, so the full agent chain for a transaction ID can be reconstructed after an incident.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
Internal services get a narrow, required scope that can only shrink along the chain, the user (sub), the delegated agent (act) and, when agents are recognised, the originating and current agent and a hop count, so they can treat agent-driven calls differently from direct human calls.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Nothing can be revoked in-band; tokens expire within minutes and new ones stop once the underlying access token is invalidated (if the service checks). Investigation is supported by the transaction ID and the Transaction Token Service's audit log.

Accountability

Goal: an action can be traced back to the parties responsible for it.
An action inside the trust domain can be traced to the user, the agent that started the chain and the agent at the current hop (at application level), with the full chain reconstructable from the audit log; session identifiers are only self-asserted hints.

Not addressed

  • Status and adoption: Individual draft -03, no deployments ()
  • Authentication of the agent or user: No, checks a token issued by the TTS (handled outside the protocol)
  • Human approval: No, outside the protocol (handled outside the protocol)
  • Revocation: No; short lifetimes instead (not addressed by the specification)
  • Contact and escalation: No contact field; txn for correlation (not addressed by the specification)
  • Cross-party signalling: No; audit logging only (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
A Transaction Token: a short-lived JWT signed by the Transaction Token Service, sent in its own Txn-Token HTTP header (not the Authorization header) on each call between workloads. The signature covers all claims (subject, scope, transaction ID, context and agentic_ctx), so they cannot be altered along the chain. It is not bound to the sender: the base draft says it is not resistant to replay, and it must not be used to authenticate a workload.
Required by the specification · requirement level: MUST
Why this rating: A defined credential on every call that the service can verify; the answer notes it is not proof of possession (as for MCP Authorization's bearer token).

Short, but with no enforced maximum. There is no maximum for verifiers to enforce, and the Transaction Token Service may issue replacement tokens that outlive the input token if its policy allows. Authentication of the agent or userDoes the receiving service itself authenticate the party making the request (the individual agent or the user)? Who exactly is authenticated, and by whom?Not addressed

Scoped authorizationDoes the protocol tell the service what the agent is allowed to do (scopes, per-action limits)? How fine-grained is it?Addressed
Yes. Every token carries a required scope describing the narrow purpose of the transaction, and usually a tctx object with immutable transaction details (e.g. action, ticker and quantity of a trade). Scope can only be narrowed when a token is replaced, never widened, and the extension adds a hop count that services should check against a maximum. Scope values and how each service turns them into a decision are left to the deployment.
Required by the specification · requirement level: MUST
Why this rating: Scoped permissions are required in every token and the service can enforce them (same as MCP Authorization).

Human approvalDoes the protocol include a step where a person approves the agent's access or action? Can the service ask for it?Not addressed

The only approval the extension mentions is by software: the agent's infrastructure layer must check model output before using it in a token request.

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
The trust domain's Transaction Token Service. There is exactly one logical service per trust domain; it decides which workloads may obtain tokens and with what content, and services accept only tokens signed for their domain. With the extension it also decides which callers count as agents, usually through an Agent Attribute Store whose posture and provenance attributes must come from the domain's deployment pipelines, not from the agents. Outside agents get only the context the domain's policy allows for unverified external actors.
Required by the specification · requirement level: MUST
Why this rating: The protocol names the party whose tokens services rely on (as MCP Authorization names the authorization server); the answer notes external agents are treated as unverified.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Not addressed
No. Neither draft defines a way to revoke a Transaction Token or an agent's access; the base draft relies on short lifetimes instead. Before issuing a token, the Transaction Token Service MAY check whether the presented access token was invalidated (e.g. through RFC 7662 introspection), which stops new tokens but not ones already issued, and it must not replace an expired token. Open questions

  • Only the table of contents of the published -03 was compared with the repository text; small wording differences between the two cannot be ruled out.
  • How receiving workloads obtain the Transaction Token Service's signing keys is not specified (the base draft says the keys are 'often' known). This could affect validity in practice.
  • The agent instance identifier was rated yellow because session_id identifies the agent's runtime session; it could be argued red because the value is self-asserted and may not be used for decisions.
  • Whether the extension's MUST for mutually authenticated channels between all components lets a resource server link the calling workload to proximate_agent.id is not stated; authentication was rated red on that basis.
  • Credential lifetime was rated yellow because no verifier-enforced maximum exists; 'on the order of minutes' could be read as a specific short limit (green).

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (68 of 68 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
