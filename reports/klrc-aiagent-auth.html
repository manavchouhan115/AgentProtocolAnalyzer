Summary

Many groups are inventing new identity and authorization protocols for AI agents. This Informational Internet-Draft argues that existing standards already cover most needs and shows how to combine them. It treats an agent as a workload, like any other running service, and gives best practices for identifying, authenticating, authorizing and monitoring it. It is written by authors from Defakto, AWS, Zscaler, Ping Identity, OpenAI and Okta. Version -03 (July 2026) is the last version under this name: the IETF WIMSE working group has since adopted it as draft-ietf-wimse-aims, which is not analysed here. No deployment of the framework itself is named.

Each agent must have exactly one workload identifier (WIMSE, possibly a SPIFFE ID) and short-lived credentials bound to a key, issued after an assessment of its environment. Services authenticate the agent with mutual TLS, WIMSE proof tokens or HTTP Message Signatures, and grant access through OAuth access tokens. The token names the agent (client_id) and the user it acts for (sub), with user approval and CIBA step-up for sensitive actions. Revocation and monitoring rely on OpenID Shared Signals, and audit logs are mandatory. It defines no new messages, no model identity, no contact channel, and no identifier for individual running copies.

How it works

  1. When an agent is deployed, its platform's provisioning system (e.g. SPIFFE) checks the agent's environment and issues it a short-lived credential bound to its unique WIMSE identifier (e.g. an X.509 certificate or a Workload Identity Token), and rotates it automatically. The language model never sees these credentials.
  2. To act for a user, the agent sends the user to the authorization server, where the user signs in (preferably with a passkey) and approves the access. The agent then authenticates with its own credential (not a static secret) to redeem an access token naming the user in sub and the agent in client_id. Acting for itself, it uses client credentials or a JWT grant.
  3. The agent calls a tool, service or LLM, authenticating with mutual TLS, a WIMSE proof token or an HTTP Message Signature using its key, and presents the access token.
  4. The service checks the agent's proof, validates the access token (directly or by introspection) and decides on the request using the agent and user identifiers, scopes and its own policy. For sensitive actions the authorization server can require extra user approval, e.g. through CIBA.
  5. Inside the service, the access token is swapped for a Transaction Token; to reach another domain, the agent uses Identity and Authorization Chaining to get a token from that domain's authorization server.
  6. Participants may subscribe to Shared Signals (CAEP or RISC) events and must stop using revoked access promptly. All parties keep tamper-evident audit logs of the agent, the user, the action and the decision.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The service authenticates the agent by its own key and receives an OAuth token naming the agent, the user it acts for and the approved scopes, with user approval and step-up for sensitive actions.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Access ends mainly through short credential lifetimes; services that subscribe to Shared Signals can cut off sessions, users or agents promptly, but subscription is optional and there is no contact channel or instance-level cut-off.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Mandatory tamper-evident audit logs record the authenticated agent, the delegated user or system, the action and the decision, so actions can be traced to the agent workload and the user, but not to a specific running copy or model.

Not addressed

  • Status and adoption: Individual draft -03, replaced by WIMSE WG draft ()
  • Agent instance identifier: Not defined (not addressed by the specification)
  • Contact and escalation: No contact field (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
A workload credential bound to the agent's key, plus an OAuth access token. The agent proves its identity with mutual TLS (X.509 certificate), a WIMSE Workload Proof Token (a signed JWT tied to the request, covering e.g. audience, expiry and a hash of the agent's token) or an HTTP Message Signature covering e.g. method, path and body digest; these are proof of possession. JWT-SVIDs and the access token are bearer tokens; -03 does not require sender-constrained access tokens. Static API keys are called an antipattern.
Part of the normal flow · requirement level: MUST
Why this rating: Cryptographically bound credentials are required and presented in the normal flow; the answer notes which options are bearer (as for MCP Authorization).

Authentication and authorization
Authentication of the agent or userDoes the receiving service itself authenticate the party making the request (the individual agent or the user)? Who exactly is authenticated, and by whom?Addressed
Yes, for the agent. The service authenticates the agent directly with the agent's own key: in the mutual TLS handshake, or per request through a WIMSE proof token or HTTP Message Signature, each tied to the agent's workload credential. Human approvalDoes the protocol include a step where a person approves the agent's access or action? Can the service ask for it?Addressed
Yes, when the agent acts for a user. The user signs in at the authorization server and explicitly approves the access before a token is issued. For risky requests the authorization server SHOULD decline or obtain more approval, e.g. through CIBA (a push to the user's phone). Confirmation inside the agent's own interface does not count: it must be tied to a grant from the authorization server. Agents acting on their own behalf need no person, and the draft notes CIBA fits mid-task approval poorly.
Part of the normal flow · requirement level: SHOULD
Why this rating: A user approval step is part of the defined delegation flow, with step-up for sensitive actions (same as MCP Authorization).

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
Two parties. The provisioning system (e.g. SPIFFE) vouches for the agent's identity: it checks signals about the agent and its environment (posture) and only then issues short-lived credentials. The authorization server vouches for access: it evaluates policy and issues the tokens the service accepts. The draft requires no particular posture mechanism or evidence, so how much the identity is worth depends on the deployment.
Part of the normal flow
Why this rating: The framework names the parties that vouch (credential provisioner and authorization server), as MCP Authorization names its authorization server.
Evidence (3)
Provisioning issues credentials after verification. Source states AI Agent Authentication and Authorization, draft-klrc-aiagent-auth-03, 8. Agent Credential Provisioning. (quote verified against the source)
“a provisioning component gathers workload and execution context signals, verifies them according to local policy, and, if verification succeeds, issues short-lived credentials for subsequent authentication and authorization.”
The authorization server evaluates policy and issues tokens. Source states AI Agent Authentication and Authorization, draft-klrc-aiagent-auth-03, 10.2. Leverage OAuth 2.0 as a Delegation Authorization Framework. (quote verified against the source)
“which receives the request, evaluate the authorization policy and returns an access token”
No posture mechanism is required. Source states AI Agent Authentication and Authorization, draft-klrc-aiagent-auth-03, 8. Agent Credential Provisioning. (quote verified against the source)

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Partly addressed
Partly. The main tool is short credential lifetimes, which the draft calls an alternative to explicit revocation. In addition, any participant MAY subscribe to OpenID Shared Signals events (CAEP or RISC, e.g. session revoked or subject disabled), and recipients must then stop using revoked authorization without undue delay. Subscription is optional and who sends which events is left open. Granularity depends on the event (a session, a user or the agent's identity).
Optional in the specification · requirement level: MAY
Why this rating: Revocation via signals is defined and enforced promptly once received, but subscribing is optional, so it may not reach every verifier; the calibration examples are red because they define none.

Notes

  • This is a best-practice framework rather than a wire protocol: it composes existing standards. Ratings count what the draft itself requires or recommends; capabilities of the referenced standards that the draft does not invoke are not counted.
  • The analysed text was taken from the authors' repository at the tag draft-klrc-aiagent-auth-03. Section numbers follow the published -03 numbering, derived from the order of headings in the source.
  • The draft has been replaced by the WIMSE working-group draft draft-ietf-wimse-aims (latest -01, 2 November 2026). The successor's commit history shows additions such as a section on sender-constrained access tokens, which could change several ratings; it was not analysed.
  • OpenID AuthZEN is listed as a normative reference in -03 but not used in the text.
  • The draft uses RFC 2119 keywords; lowercase 'may' in descriptive text (e.g. 'Agents may authenticate using a variety of mechanisms') was not treated as a requirement. No instructions aimed at AI tools were found in the sources.

Open questions

  • Does 'agent' in 'Agents MUST be uniquely identified' mean each running copy or the agent as a deployed service? The draft does not say; the identifier was rated yellow and the instance identifier red on that basis.
  • Authentication was rated green because every described mechanism uses the agent's own key, but the draft offers these as options rather than requiring one. Whether a deployment may skip agent authentication and rely on the access token alone is not stated.
  • Which parties transmit Shared Signals events about agents, and with what subject identifiers (WIMSE ID, client_id), is not specified, so how revocation reaches a given service is unclear.
  • How a receiving service in another trust domain obtains the keys to verify an agent's workload credential is not described.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (61 of 61 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
