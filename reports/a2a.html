Summary

The Agent2Agent (A2A) Protocol is an open standard for AI agents built by different vendors and frameworks to discover each other, hand over tasks and exchange results, without sharing their internal memory or tools. One agent (the A2A client) sends messages and tasks to another agent (the A2A server, or remote agent), which publishes an Agent Card describing what it can do and how callers must authenticate. Google started the project in April 2025; it is now maintained under the Linux Foundation. Version 1.0 was released in March 2026 as the first stable version, and v1.0.1 (May 2026) is the latest release. Microsoft Foundry Agent Service, among others, serves it.

For identity and access, A2A deliberately reuses standard web security rather than defining its own. The server lists in its Agent Card which schemes it accepts (API key, HTTP authentication such as a bearer token, OAuth 2.0, OpenID Connect or mutual TLS); the client obtains credentials outside A2A and sends them with every request, and the server must authenticate and authorize every request. A2A messages themselves carry no user or client identity. Agent Cards can be signed, which helps the client trust the server, not the other way round. A2A defines a task state for asking the client to obtain extra authorization mid-task, but no client agent identifier, credential lifetime, revocation, contact channel or model identity.

How it works

  1. The A2A server (the receiving agent) publishes an Agent Card, e.g. at /.well-known/agent-card.json, describing its skills, endpoints and the security schemes and scopes it requires. The card may be signed with JWS.
  2. The A2A client (the calling agent or application) reads the Agent Card and picks a protocol binding (JSON-RPC, gRPC or HTTP+JSON) and a security scheme.
  3. The client obtains the matching credential outside A2A, e.g. an OAuth access token from the authorization server named in the card, an API key, or a client certificate for mutual TLS.
  4. The client sends a message (e.g. SendMessage) with the credential in an HTTP header or gRPC metadata on every request. A2A messages carry no user or client identity of their own.
  5. The server authenticates the request with its declared scheme, applies its own authorization policy (e.g. per-skill scopes), and creates or continues a task. If it needs more authorization during the task, it sets the task to TASK_STATE_AUTH_REQUIRED and the client arranges it outside A2A.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The receiving agent must authenticate and authorize every request with the scheme it declared, and can require OAuth scopes per skill, but what is checked and how finely is left to each agent and to the external credential issuer.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
A2A defines no revocation; a misbehaving caller can be cut off only through the credential scheme (e.g. deleting its API key or revoking its OAuth grant), at the granularity that scheme gives, which is usually a client or user, not an agent instance.

Accountability

Goal: an action can be traced back to the parties responsible for it.
An action can be traced only to whatever identity the credential carries (a key holder, an OAuth client, a user or a certificate subject); A2A messages add no caller, user or model identity.

Not addressed

  • Identifier: None for the calling agent (handled outside the protocol)
  • Agent instance identifier: No (not addressed by the specification)
  • Acting for (authority): No; depends on chosen auth scheme (handled outside the protocol)
  • Credential lifetime: Not specified (not addressed by the specification)
  • Authentication of the agent or user: Credential check only; scheme decides whose (handled outside the protocol)
  • Revocation: Recommended, not defined (not addressed by the specification)
  • Contact and escalation: No for callers (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
Yes, a credential on every request, of a type the server chooses. The Agent Card declares one or more security schemes (API key, HTTP authentication such as a bearer token, OAuth 2.0, OpenID Connect, or mutual TLS); the client sends the credential in headers or gRPC metadata on every request, and the server must authenticate each one. Except for mutual TLS, these are bearer credentials: whoever holds them can use them. For credentials passed in-band during a task, the spec recommends binding them to the requesting agent but defines no mechanism.
Required by the specification · requirement level: MUST
Why this rating: A credential declared by the server is presented on every request and must be verified (same as MCP Authorization); the answer notes most schemes are bearer credentials.

Partly. During a task, the server can set the task to TASK_STATE_AUTH_REQUIRED to ask the client to obtain authorization, and the spec gives human approval before a destructive action as an example. The approval itself happens outside A2A: the client may pass the request to a person, another agent or a service, and credentials are delivered out of band. A user approval step in an OAuth flow, if used, also happens outside A2A.
Optional in the specification · requirement level: MAY*
Why this rating: A defined but optional way for the service to request approval, which may be fulfilled by software rather than a person; MCP Authorization is green because user approval is part of its main flow.

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Partly addressed
Partly. The server chooses its schemes, and for OAuth 2.0 and OpenID Connect the Agent Card points to the issuer, so a valid token means that issuer approved the client. For API keys and HTTP authentication the server is its own issuer, and the mutual TLS scheme names no certificate authority. Signed Agent Cards and registries help the client trust the server, not the server trust the client.
Optional in the specification
Why this rating: A vouching party is named only in some schemes; MCP Authorization is green because clients must use tokens from the server's named authorization server.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Not addressed
Not defined by A2A. The security considerations say agents should implement credential revocation mechanisms, but A2A defines none, so revocation depends on the chosen scheme: the server can delete an API key it issued, or the OAuth authorization server can revoke tokens (e.g. under RFC 7009), with the speed and granularity that scheme allows. The revocation rule for signing keys covers Agent Card signatures, which the client checks, not request credentials.
Not addressed by the specification · requirement level: SHOULD
Why this rating: A2A only recommends (SHOULD) that agents have revocation and defines no mechanism, so coverage is none (same colour as all three calibration examples, which also leave revocation to other parties).

Notes

  • A2A is analysed from the side of the A2A server (the receiving agent). Many A2A identity features, such as the Agent Card and its signatures, help the calling agent trust the server, not the reverse; the rows say so where relevant.
  • A2A uses RFC 2119 keywords. The human approval row rests on lowercase wording ("provides the capability", "may"), so its requirement is marked MAY*.
  • Two rows also cite the A2A documentation page Enterprise Implementation of A2A, which is non-normative; it is used only where it repeats or explains the specification (e.g. that A2A payloads carry no user or client identity).
  • The specification file at the v1.0.1 tag still shows "Latest Released Version 1.0.0" in its header; the changelog dates v1.0.1 to 2026-05-26 and the git tag to 2026-05-28.
  • A Secure Passport extension is listed among example extensions in the A2A documentation; it lives in the samples repository, is not part of the specification and was not counted.
  • The Microsoft Learn page could not be checked by the script; its quote was checked with a web tool.

Open questions

  • Section 7.4 requires the server to authenticate every request. Does the project intend this to identify the calling agent, or only to validate the credential of the declared scheme?
  • The mutual TLS scheme object carries only a description. How is a server expected to tell clients which certificate authorities or certificates it accepts?
  • The v1.0.1 sample Agent Card uses a "security" field while the normative proto names it security_requirements (the v1.1.0 release candidate updates the sample). Implementations may differ on this.
  • Section 7.6.3 recommends binding in-band credentials to the requesting agent but gives no mechanism. Is an official extension planned for this?

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (64 of 64 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
