Summary

Many AI agent platforms register one OAuth client and run thousands of agent sessions under it, so a service receiving their access tokens sees only the platform, never the specific agent. The OAuth 2.0 AI Agent Instance Profile tries to fix this by giving each running agent instance its own attested identifier and carrying it into the access tokens that services receive. It is aimed at agent platforms, authorization servers and the APIs or MCP servers they call. It is an individual Internet-Draft by Karl McGuinness, version -00 from July 2026, with no named deployments, and the author has since marked it superseded and not being progressed.

It is a profile of a companion draft, the OAuth 2.0 Client Instance Assertion. An Agent Attester (usually the platform's control plane) signs evidence naming the instance (agent_instance_id), optionally its platform, model and runtime, and binds it to a key the instance holds. The authorization server checks this evidence and issues an access token that names the user in sub and the agent instance in act.sub, and that is bound to the instance's key (DPoP or mutual TLS, never a bearer token). Sub-agents get nested act chains through token exchange. The profile leaves agent permissions, contact channels and signals between services out, and its model claims are only as reliable as the Attester.

How it works

  1. The agent platform registers its OAuth client for the profile (ai_agent_instance_profile set to true) and names its Agent Attester, either in its instance_issuers client metadata or by agreement with an authorization server that trusts that Attester.
  2. When the platform starts an agent instance (a session, task or runtime), the Agent Attester mints signed evidence for it: a unique agent_instance_id, optional agent_platform, agent_model and agent_runtime claims, and a cnf claim binding a key that only this instance holds.
  3. The instance asks the authorization server for a token (e.g. redeeming an authorization code after the user approved the client), presenting the evidence and a DPoP proof. The authorization server checks the signature, the client binding, replay and possession of the bound key.
  4. The authorization server issues a sender-constrained access token: sub names the user, act.sub names the agent instance with sub_profile ai_agent, and the model may be surfaced if local policy allows. For a self-acting agent the instance itself is sub.
  5. The instance calls the resource server (e.g. an MCP server) with the token and a fresh proof of possession. The resource server validates both and can key policy, rate limits and audit records on the instance, not only on the platform.
  6. If the instance spawns a sub-agent, the sub-agent exchanges the token while presenting its own evidence, producing a nested act chain. If an instance misbehaves, the authorization server can revoke all tokens for that one instance.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The service sees which agent instance, on which platform and for which user, holds a key-bound token with the grant's OAuth scopes, so it can apply its own per-agent rules (e.g. read-only for older models); agent permissions themselves are not defined.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Access can be cut off for one agent instance without affecting the platform's other agents, through per-instance revocation at the authorization server, but only promptly for services that use introspection; how revocation is triggered and how the service reports a problem are not defined.

Accountability

Goal: an action can be traced back to the parties responsible for it.
An action can be traced to the user, the platform (client_id) and the specific agent instance, including each sub-agent in a delegation chain, and optionally to the model; how much this is worth depends on the Attester, which is usually the platform itself.

Not addressed

  • Status and adoption: Individual draft -00, superseded, no deployments ()
  • Contact and escalation: No contact channel defined (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
An OAuth access token that must be sender-constrained: bound through DPoP or mutual TLS to a key specific to that agent instance, so a stolen token alone cannot be used. Bearer tokens are forbidden under the profile. On each request the instance presents the token plus a proof of possession (a DPoP proof signed with its key, or the TLS client certificate). The token can be a JWT or an opaque token checked through introspection.
Required by the specification · requirement level: MUST
Why this rating: A defined credential on every request that the service can verify, here with proof of possession (stronger than MCP Authorization's bearer token).

Scoped authorizationDoes the protocol tell the service what the agent is allowed to do (scopes, per-action limits)? How fine-grained is it?Partly addressed
Partly. Tokens carry the normal OAuth scopes of the underlying grant, and when a sub-agent exchanges a token the scope can be narrowed at each hop under Token Exchange. The profile itself defines no agent capability or tool permissions and says fine-grained permissions come from Rich Authorization Requests (RFC 9396) or a deployment's own scope design. What it adds is per-instance identity, so a service can enforce its own limits per agent rather than per platform.
Part of the normal flow
Why this rating: Tokens carry ordinary OAuth scopes in the normal flow, but the profile defines no permissions of its own and puts agent permissions out of scope; chosen as the lower of yellow and green.

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
The Agent Attester vouches for each instance, and the authorization server only issues tokens for instances with valid evidence from an Attester it accepts. With the assertion carrier, the platform lists its Attesters in its client metadata; with the attestation carrier, the authorization server configures which Attesters it trusts. The draft names three assurance tiers: platform self-attestation (the usual case), hardware-rooted and independent attestation. Deployments must not present self-attestation as one of the stronger tiers.
Required by the specification · requirement level: MUST
Why this rating: The protocol names the parties that vouch (Attester and authorization server), as MCP Authorization names its authorization server; the answer notes the usual tier is self-attestation.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Partly addressed
Partly. The base specification defines per-token revocation (RFC 7009) and a per-instance mode, keyed on the Attester and instance identifier, that invalidates all of one agent's tokens without touching the platform's other agents. Authorization servers SHOULD support the per-instance mode, and introspection must then report those tokens inactive. How revocation is triggered is out of scope, and a resource server validating JWTs locally keeps accepting a revoked token until it expires.
Optional in the specification · requirement level: SHOULD
Why this rating: Revocation is defined at instance granularity but is only recommended and reaches services that validate JWTs locally only at expiry; MCP Authorization is red because it defines none.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (66 of 66 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
