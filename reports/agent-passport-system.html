Summary

The Agent Passport System (APS) describes how to represent and check the authority behind an AI agent's actions. It covers who the agent is, whom it acts for, what it was delegated, whether a gateway admitted a specific action, and what was observed afterwards. It is aimed at deployments where agents call tools and APIs through an enforcement gateway, such as MCP servers or enterprise APIs. It is a single-author individual Internet-Draft, at revision -04 of September 2026, with intended status Informational. Its own implementation appendix lists only the author's open-source packages and says they do not establish independent implementation or adoption.

Each agent has a self-signed Ed25519 'passport' with a DID identifier. A principal can sign a separate binding saying the agent acts for it, and authority comes from signed delegation records with seven facets that can only narrow down a chain (scope, spend, depth, time, reputation, values, reversibility). For each action the agent signs an 'action intent' that commits to the target, payload, scopes, time and a nonce. An enforcement gateway verifies the chain, rechecks revocation, issues a single-use approval and records signed receipts. Revocation cascades to descendants, and an unknown revocation state is treated as not active. Trust in a chain's root is left to the verifier's policy. No contact channel, signalling between services or model identity is defined, the target system itself has no obligations, and the guarantees rely on all privileged calls going through the gateway.

How it works

  1. The agent creates an Ed25519 key and a self-signed Agent Passport with a DID (e.g. did:key) and an expiry. A principal (a person, office or organisation) can sign a Principal Binding saying the agent acts for it, scoped to named audiences.
  2. An authority issuer (e.g. the principal) signs an AuthorityDelegation to the agent with seven required facets, e.g. scope commerce:checkout, a spend limit, depth, a time window, a reputation ceiling, required values and a reversibility ceiling. The agent can delegate onward, but each child can only narrow its parent.
  3. To act, the agent computes an action_ref over its ID, the action type, the exact target, a payload hash, the scopes needed, the time and a nonce, and signs an action-intent record naming the delegation it relies on.
  4. The enforcement gateway in front of the target verifies the signatures, resolves keys at signing time, and checks the whole delegation chain (root accepted by its trust policy, attenuation, time, revocation). It applies its policy and signs a policy-decision record: permit, deny or narrow, with a bounded lifetime.
  5. At dispatch, the gateway consumes that single-use approval, rechecks revocation and time, and reserves spend against every bounded ancestor. It then calls the target itself, using credentials only it holds.
  6. The gateway signs an action-result record of what it observed. Verifiers can later check the receipt chain, and any party can revoke delegations it issued, which invalidates all chains that contain them.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
A gateway that implements APS can check, for each action, the agent's own signature, the full narrowing delegation chain and seven kinds of limits, including cumulative spend, before it calls the target itself. Protection holds only for calls that go through that gateway.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
An issuer can irreversibly revoke a single delegation or a whole subtree, and gateways must recheck before every dispatch and treat unknown status as not active. How revocation status is distributed, and how outside counterparties are told, is left to profiles and open questions.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Signed intent, decision and result receipts tie each action to an agent key, a delegation chain and the gateway's decision. The principal behind the authority can be named and signed, but linking it to the chain used is not yet defined.

Not addressed

  • Status and adoption: Individual draft -04; author's implementations only ()

  • Model identity: No (not addressed by the specification)

Who is being identified?
IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Addressed
Yes. Each agent has its own DID (agent_id), carried in a self-signed Agent Passport and bound to the agent's own Ed25519 key. With did:key the identifier is the key. Agents that receive delegated authority (delegates and sub-agents) have their own passports, so the identifier names an individual agent rather than its provider. The passport proves possession of the key. Whether that key is authorised for the DID is resolved separately under the DID method.
Required by the specification · requirement level: MUST
Why this rating: The identifier names the individual agent through its own key, not a provider-level key or client ID (the calibration examples are yellow because their identifiers are provider-level).

Authentication and authorization
Authentication of the agent or userDoes the receiving service itself authenticate the party making the request (the individual agent or the user)? Who exactly is authenticated, and by whom?Addressed
Yes, the agent. Each action intent is signed with the acting agent's own key, and the verifier checks that the action input's agent_id equals the record's subject_agent and that the signer's key was authorised for that DID at signing time. This authenticates the individual agent per action, not just its provider. Users and principals are not authenticated at the gateway. Their binding signatures are verified, but who they are is left to the verifier's trust policy. The draft notes that a compromised agent can still produce valid signatures.
Required by the specification · requirement level: MUST

Scoped authorizationDoes the protocol tell the service what the agent is allowed to do (scopes, per-action limits)? How fine-grained is it?Addressed
Yes. Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Addressed
Yes. Any delegation can be revoked, irreversibly, by its issuer. The gateway must recheck revocation at the moment it consumes an approval to dispatch, not only when it decided. Once a verifier has established a revocation, it must reject every chain containing the revoked delegation, so descendants fall with it. An unknown, stale or unrecognised revocation state is not treated as active. Granularity ranges from one delegation (one agent's grant) to a whole subtree, and principal bindings can be revoked separately. Where revocation status comes from, and how fresh it must be, is left to profiles.
Required by the specification · requirement level: MUST
Why this rating: Revocation is defined, an unknown status is treated as not active, and the gateway must recheck it at each dispatch (all three calibration examples are red because they define none); how status is distributed is left to profiles.

Notes

  • The specification uses RFC 2119 keywords.
  • Requirements are split into APS Core and opt-in Candidate features, and most lifecycle and decision-to-effect material is Candidate. Ratings rest on Core sections (passport, principal binding, delegation, chain verification, revocation rechecks, policy chain, receipts) unless an answer says otherwise.
  • The analysis takes the enforcement gateway (APS's 'enforcement boundary') as the receiving service. The draft gives the target system itself no interface and no obligation, and its protections hold only when all privileged calls go through the gateway (the 'mediation assumption').
  • The -04 text is 271 pages. It was read in the browser from the ietf.org archive .txt because neither ietf.org nor datatracker could be reached from the analysis workspace, and the author's repository holds only -00 to -02. Every quote was checked by exact matching against the full -04 text in the browser.
  • Name collision: the earlier AGNTCY Identity draft used 'Agent Passport' for its credential, and other products use the phrase. This analysis covers only draft-pidlisnyi-aps-04.

Open questions

  • How does a gateway obtain revocation status (sources and freshness bounds are profile-defined), and is there a default profile?
  • How should a verifier associate a principal binding with the accepted root of a delegation chain (Section 19.2.10)?
  • Who is expected to operate the enforcement gateway: the agent's organisation, the target service, or a third party? The draft does not say.
  • Where does the 'resolved subject score' for the reputation facet come from?

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (56 of 56 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-20. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
