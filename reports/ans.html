Summary

The Agent Name Service (ANS) gives each AI agent a verifiable name tied to a domain name, so that one agent can check that another really belongs to the organisation it claims and is running the software version it registered. It answers questions like whether a supplier's invoicing agent is genuine or a look-alike. ANS grew out of an OWASP paper and IETF draft; GoDaddy built and runs a production registry, and the project is now a Linux Foundation series (LF Projects). The specifications in its GitHub repository are marked DRAFT and are newer than the companion IETF draft, an individual submission whose -01 revision dates from April 2026.

An agent operator registers an agent with a Registration Authority (RA), proving control of its domain. The RA issues certificates, including an Identity Certificate naming the agent and version (ans://v1.0.0.agent.example.com), publishes DNS records and seals every event into a public, append-only Transparency Log. When one agent calls another, the callee checks the caller's certificate (by mutual TLS or a per-request DPoP proof) plus a log receipt and a short-lived status token, so revoked agents are refused within about an hour. ANS deliberately covers authentication only: authorization, acting on behalf of users, trust scoring and contact details are left to the service or to other specifications.

How it works

  1. The agent's operator registers the agent at a Registration Authority (RA): it proves control of the agent's domain (ACME DNS-01) and submits certificate requests, receiving a Server Certificate and, optionally, an Identity Certificate from the RA's private CA that names the agent and version.
  2. The RA seals an AGENT_REGISTERED event into the Transparency Log (TL), and the operator publishes DNS records, including an _ans-badge record pointing to the agent's entry in the log.
  3. In the background, the calling agent fetches its own log receipt (proof its registration is in the log) and a status token (proof it is currently active, valid for about an hour).
  4. On each request, the caller proves possession of its Identity Certificate key: in the TLS handshake (Method A, mutual TLS) or with a signed DPoP proof bound to the method, URL and content (Method B), sending the receipt and status token in HTTP headers.
  5. The callee (the receiving agent) verifies the certificate or proof, the receipt and status token against the TL's keys (or queries a trusted TL for the badge), checks that names and fingerprints match and that the agent is not revoked, then applies its own authorization policy.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
ANS gives the receiving agent a strongly authenticated identity for the specific calling agent and version, but no permissions; the receiving agent must apply its own authorization (or OAuth) to that identity.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
A misbehaving agent version can be revoked by its operator or the RA and is refused by verifiers within about one to two hours on the recommended tier; integrity problems can be flagged by independent monitors. There is no contact channel and no way to stop one running copy.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Actions can be traced to a specific agent and version at a verified domain, with a public log history and, if linked, a verified operator identity; not to a user or an AI model.

Not addressed

  • Agent instance identifier: No (not addressed by the specification)
  • Acting for (authority): No; delegation out of scope (explicitly out of scope)
  • Scoped authorization: No; out of scope (explicitly out of scope)
  • Human approval: No (not addressed by the specification)
  • Contact and escalation: No; RA collects no contact info (not addressed by the specification)
  • Model identity: No; software version only (not addressed by the specification)

Who is being identified?
IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Addressed
Yes, per agent. Each registered agent has an ANSName, ans://v{version}.{agentHost}, built from its own domain name and software version, which its Identity Certificate carries and the callee extracts. Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed

With Method A the caller presents its Identity Certificate in mutual TLS; with Method B it sends a DPoP proof signed with that certificate's key, bound to the HTTP method, URL and content hash and usable once, plus a log receipt and status token in headers. Both prove the caller holds the private key; a conformant callee implements at least one method.
Required by the specification · requirement level: MUST
Why this rating: A defined, verifiable proof-of-possession credential on every connection or request (all three calibration examples are green; unlike MCP Authorization this is not a bearer credential).

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Addressed
Short, and enforced by the verifier. The status token, which says the agent is currently active, has a default lifetime of one hour, and verifiers must reject it after expiry (allowing at most ten minutes of clock skew). Method B proofs must have been created within a freshness window (120 seconds by default) and are single-use. The certificate's own validity period, set by the CA, must also contain the current time.
Required by the specification · requirement level: MUST
Why this rating: Specific short limits that verifiers must enforce (same as Visa TAP's eight-minute rule).

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
The Registration Authority and its Transparency Log, as notaries. The RA issues an Identity Certificate only after the operator proves control of the agent's domain, and the log publicly records it; verifiers choose which logs to trust through an explicit allowlist. The RA vouches for control and registration, not for good behaviour: it calls itself a notary, not a judge, and trust scoring lives in a separate Trust Index specification.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Addressed
Yes. The operator or the RA can revoke an agent version's registration; the RA revokes its Identity Certificates, seals an AGENT_REVOKED event with a reason, and the operator removes its DNS records. The log then refuses fresh status tokens and badges show REVOKED, and verifiers must treat a missing fresh token as revocation, so it reaches callees within the token lifetime (worst case about two hours with defaults). On the badge tier the delay depends on each deployment's cache settings.
Required by the specification · requirement level: MUST
Why this rating: Revocation is defined at agent-version granularity and reaches verifiers within a bounded time (all three calibration examples are red because they define none); badge-tier latency is deployment-configured, noted in the answer.
Evidence (4)
AGENT_REVOKED event with reason. Source states ANS-1: Registration & Lifecycle (spec/ans-1-registration.md, v0.2.0), 6.2 AGENT_REVOKED. (quote verified against the source)
“Emitted when the AHP or RA revokes a registration.”
Missing fresh status token equals revocation. Source states ANS-6: Agent-to-Agent Authentication (spec/ans-6-agent-authentication.md, v0.2.0), 4.4 Status token. (quote verified against the source)
“Verifiers MUST treat the inability to obtain a fresh status token as equivalent to revocation, subject to the failure policy in §9.”
Revocation latency bound. Source states ANS-6: Agent-to-Agent Authentication (spec/ans-6-agent-authentication.md, v0.2.0), 11.1 Revocation latency. (quote verified against the source)
“On the SCITT tier the worst case is status-token TTL + clock skew + grace: one hour by default”
Badge-tier bounds are deployment configuration. Source states ANS-6: Agent-to-Agent Authentication (spec/ans-6-agent-authentication.md, v0.2.0), 11.1 Revocation latency. (quote verified against the source)
“both deployment configuration rather than spec-bounded”
Contact and escalationCan the service contact whoever is responsible for the agent (agent provider, user, model provider) if something goes wrong? Is a contact field required, optional or absent?Not addressed
No. ANS defines no contact or abuse channel for an agent's operator; the specification notes that the RA collects no contact information. A callee can see the agent's domain name and, if linked, a Verified Identity of the operator (e.g. a Legal Entity Identifier), which helps to find the responsible party outside ANS.
Not addressed by the specification
Why this rating: No contact channel is defined (same as all three calibration examples).
Evidence (2)
The RA collects no contact info. Source states ANS-0: Identity (spec/ans-0-identity-anchor.md, v0.2.0), 6. Identity links. (quote verified against the source)
“The RA pushes nothing (it collects no contact info, and the account it could notify is the one whose credential performed the link).”
Verified Identities can name a legal entity, e.g. an LEI. Source states ANS-0: Identity (spec/ans-0-identity-anchor.md, v0.2.0), 2. Terminology. (quote verified against the source)
“Identifier — a public, stable string an operator controls: an FQDN, a DID, an LEI.”
Monitoring and provenance
Cross-party signallingCan one service warn others about a misbehaving agent (shared signals, reputation, abuse reports)?Partly addressed
Partly. Independent integrity monitors can report discrepancies (e.g. live DNS records or certificates that differ from what was sealed); after corroboration the RA can seal a warning that every verifier can read, and consumers decide how to react. These signals cover infrastructure integrity only: the RA does not judge behaviour, and behaviour-based reputation lives in the separate Trust Index specification, not in ANS.
Optional in the specification
Why this rating: A defined cross-party channel exists but is limited to infrastructure integrity, and how findings reach the registry is implementation-defined; behavioural signalling is in a companion specification.
Evidence (4)
Quorum before the RA acts; findings are verifiable. Source states ANS-5: Integrity Monitoring (spec/ans-5-integrity-monitoring.md, v0.1.0), 7. Integrity reporting principles. (quote verified against the source)
“The RA MUST NOT act on an unconfirmed finding.”
Consumers act on confirmed findings. Source states ANS-5: Integrity Monitoring (spec/ans-5-integrity-monitoring.md, v0.1.0), 7.1 Warning, not state change. (quote verified against the source)
“When a finding meets the quorum requirement, consumers of the finding take action per their own policy.”
The RA does not evaluate behaviour. Source states ANS-5: Integrity Monitoring (spec/ans-5-integrity-monitoring.md, v0.1.0), 7. Integrity reporting principles. (quote verified against the source)
“The RA does not evaluate an agent's behavior or quality.”
Integration of findings is implementation-defined. Source states ANS-5: Integrity Monitoring (spec/ans-5-integrity-monitoring.md, v0.1.0), 7.1 Warning, not state change. (quote verified against the source)
“The registry ingests these findings through an implementation-defined integration.”
Model identityDoes the service learn which AI model (and version) is behind the agent? Is it verifiable or self-asserted?Not addressed
No. ANS records which software version of an agent is registered, as a semantic version in its name and certificate, and new code means a new version and certificate; it can also seal hashes of the agent's metadata card. The version number is declared by the operator and nothing identifies the AI model behind the agent.
Not addressed by the specification
Why this rating: No model identity; the declared software version is not counted as model identity (same as all three calibration examples).
Evidence (2)
The certificate binds a software version. Source states ANS-2: Versioned Naming (spec/ans-2-versioned-naming.md, v0.3.0), 3. The Identity Certificate. (quote verified against the source)
“Binds the certificate to a specific software version, presentable as a TLS client certificate”

Notes

  • Name collisions: draft-song-anp-ans ("Agent Name System", ANP suite), draft-hood-agtp-discovery (AGTP Agent Discovery and Name Service) and the replaced draft-narajala-ans-00 (ANS v1) are different documents. The Trust Index specification is a separate project, explicitly not an ANS layer.
  • The analysis is from the side of the callee (the receiving agent) authenticating a calling agent under ANS-6. Callee authentication by the caller (Section 5) is also defined but is not what this framework rates.
  • The repository specifications (pinned commit 9284c7e) are rated, because the project's DESIGN.md calls them authoritative. They are newer than IETF draft -01 and differ from it (e.g. ANS-6's badge and SCITT tiers and Methods A and B versus the draft's Bronze, Silver and Gold tiers).
  • Quotes from the IETF archive, GoDaddy and MuleSoft pages could not be downloaded by the script and were checked with a web tool.
  • The GoDaddy and MuleSoft deployments are documented for GoDaddy's registry; the sources do not say which ANS specification version they implement.

Open questions

  • ANS-5 says ANS-1 specifies the INTEGRITY_WARNING event, but ANS-1's event set lists only AGENT_REGISTERED, AGENT_REVOKED and reserved types. Is INTEGRITY_WARNING part of the wire contract?
  • Identity Certificates are optional at registration. How common are registrations that can only be authenticated as callees (Server Certificate) and not as callers?
  • Should multiple running copies of an agent share one Identity Certificate key, or may each have its own (rotation is additive)? The specifications do not say.
  • Will the IETF draft be revised (-02) to match the repository specifications, given that -01 has passed its expiry date?

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (59 of 59 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
