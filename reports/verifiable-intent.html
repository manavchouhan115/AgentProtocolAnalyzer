Summary

Verifiable Intent (VI) gives merchants and payment networks signed proof of what a user allowed an AI shopping agent to buy, and that the agent stayed within it. It addresses a gap in agentic commerce: today's payment systems assume a person is present at checkout, so nobody can check whether an agent's purchase matches the user's wishes. Mastercard publishes and maintains it, co-developed with Google and aligned with Google's AP2 and UCP. It is an open draft (v0.1) under Apache 2.0, with a Python reference SDK; Mastercard has announced plans to integrate it into its Agent Pay APIs.

VI is a credential format, not a transport: it rides inside other commerce protocols. It chains three layers of selective-disclosure JWTs (SD-JWT). A card issuer signs a long-lived credential binding the user's key; the user signs a mandate with either the final cart and payment (Immediate mode) or limits such as amount, merchants and products plus the agent's key (Autonomous mode); in Autonomous mode the agent signs short-lived final values for the merchant and the payment network. Each party sees only its part. VI leaves out revocation (deferred), transport, agent key provisioning, contact channels, cross-party signalling and model identity.

How it works

  1. Setup: the user registers a public key with a card issuer (a bank or payment network such as Mastercard), which signs a Layer 1 (L1) credential binding that key to an opaque user identifier and card details. It sits in a Credential Provider's wallet and lasts about a year.
  2. When the user asks an agent to buy something, the user (or a wallet holding the user's key) signs a Layer 2 (L2) credential: either the final cart and payment values (Immediate mode, valid about 15 minutes) or constraints such as amount range, allowed merchants and products, plus the agent's public key (Autonomous mode, typically 24 hours to 30 days).
  3. In Autonomous mode the agent picks the products, obtains the checkout contents and signs two Layer 3 (L3) credentials with its own key, valid about 5 minutes and at most 1 hour: L3b with the checkout for the merchant and L3a with the payment for the payment network, linked by a shared hash.
  4. The agent hands the chain to the merchant and the payment network inside whatever commerce protocol is in use, disclosing only the checkout parts to the merchant and only the payment parts to the network.
  5. The merchant verifies the issuer's signature on L1 using the issuer's published keys, the user's signature on L2, the agent's signature on L3b (in Autonomous mode), the hash links and expiry times, and checks the checkout against the disclosed constraints and its own records.
  6. The payment network does the same for the payment side, checks payment constraints, enforces one purchase per mandate and tracks cumulative spend, then routes the authorization; the issuer makes the final decision.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The merchant can check that a purchase was authorized by an issuer-known user and stays within user-signed limits (merchants, items, amounts), and the payment network enforces payment limits and budgets. VI does not control access to the merchant's other endpoints.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
There is no revocation in v0.1; short agent credentials and mandate expiry limit damage, an issuer can pull a signing key (affecting all its credentials) or block the card. A single delegation cannot be cut off early, and there is no contact channel.

Accountability

Goal: an action can be traced back to the parties responsible for it.
The chain gives signed evidence linking the issuer, a pseudonymous user, the user's exact instructions and, in Autonomous mode, the agent key that executed, which any party can verify in a dispute. It identifies the agent platform only by URL and not the model.

Not addressed

  • Revocation: Not defined in v0.1; short lifetimes (not addressed by the specification)
  • Contact and escalation: No (explicitly out of scope)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No; attestation slot without schemes (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Partly addressed
Partly, per purchase rather than per request. The merchant receives a chain of SD-JWTs signed with ES256: the issuer's Layer 1, the user's key-bound Layer 2 and, in Autonomous mode, the agent's Layer 3b. Each later layer is signed with the key named in the previous one, which is proof of possession, and carries a nonce, an audience, issue and expiry times and a hash of the layer below. VI defines no transport, so it is presented with the purchase, not on every HTTP request.
Required by the specification · requirement level: MUST
Why this rating: A strong, verifiable credential, but defined only for the purchase presentation and not for every request to the merchant (transport is out of scope); borderline green.

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Partly addressed
Partly. The agent's Layer 3 must not exceed 1 hour (5 minutes recommended), and an Immediate-mode Layer 2 should last no more than 15 minutes. Verifiers must reject any layer whose expiry has passed (with about 300 seconds of clock skew). However, the user's Autonomous delegation (Layer 2) may last up to 30 days or longer, up to the Layer 1 expiry of about a year, and verifiers are not told to reject Layer 3 credentials issued with a window longer than 1 hour.
Required by the specification · requirement level: MUST
Why this rating: The 1-hour maximum is a rule for the agent, not one verifiers are told to enforce, and the delegated authority itself can last weeks (stricter than Web Bot Auth, but not Visa TAP's verifier-enforced window); borderline green.

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
The card issuer and the user. The issuer, called a trusted third party, signs Layer 1 to vouch for the user and the user's key; the user then vouches for the agent by binding its key in a signed mandate. Only agents a verified user has delegated to can produce a valid chain. Nobody vets the agent platform itself, and VI does not say how a merchant decides which issuers to accept.
Part of the normal flow · requirement level: MUST
Why this rating: Named parties vouch (the issuer for the user, the user for the agent), comparable to MCP Authorization's authorization server plus user consent.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Not addressed
Not defined. Version 0.1 has no credential revocation; the specification lists it as a known limitation and names Token Status List as a candidate. Meanwhile, short lifetimes limit exposure, an issuer can remove a compromised signing key from its JWKS (which invalidates every Layer 1 signed with it), and issuers keep their usual card-level blocks. A single delegation cannot be revoked before it expires, so an Autonomous mandate can stay usable for weeks.
Not addressed by the specification
Why this rating: Revocation is not defined; key removal is coarse and outside the per-delegation level (same as the three calibration examples).
Evidence (3)
No revocation protocol. Source states Verifiable Intent, Security Model and Threat Analysis (spec/security-model.md), 6.1 Revocation. (quote verified against the source)
“VI v0.1 does not define a credential-layer revocation protocol.”
JWKS key removal for issuer key compromise. Source states Verifiable Intent, Security Model and Threat Analysis (spec/security-model.md), 6.1 Revocation. (quote verified against the source)
“For L1 signing key compromise, the Issuer SHOULD remove the key from its JWKS endpoint, which invalidates all credentials signed with that key.”
Expiry is the main limit on delegated authority. Source states Verifiable Intent, Security Model and Threat Analysis (spec/security-model.md), 6.7 L2 Lifetime Considerations. (quote verified against the source)
“L2 expiration is the primary mechanism for time-bounding delegated authority in the absence of revocation.”
Contact and escalationCan the service contact whoever is responsible for the agent (agent provider, user, model provider) if something goes wrong? Is a contact field required, optional or absent?Not addressed
No. VI defines no contact or escalation field for the agent, its platform or the user. It provides evidence for disputes but leaves dispute initiation, routing and escalation to payment network rules; the issuer and payment network are known parties through the chain.
Explicitly out of scope
Why this rating: No contact channel; dispute choreography is explicitly out of scope.
Evidence (2)
Dispute routing and escalation are not defined. Out of scope per Verifiable Intent, Security Model and Threat Analysis (spec/security-model.md), 2.5 Dispute Evidence. (quote verified against the source)
“VI does not define how disputes are initiated, routed between parties, escalated, or resolved.”
Searched the claim tables of all three layers for contact or support fields. None is defined. Not found in Verifiable Intent, Credential Format Specification (spec/credential-format.md), 3.3, 4.3, 5.3 claim tables.
Monitoring and provenance
Cross-party signallingCan one service warn others about a misbehaving agent (shared signals, reputation, abuse reports)?Not addressed
No. The payment network keeps state across transactions to enforce one purchase per mandate and cumulative budgets, and the user's mandate may carry device risk data for issuers, but VI defines no way for merchants or networks to warn one another about a misbehaving agent.
Not addressed by the specification
Why this rating: Not addressed.

Notes

  • No name collision found for 'Verifiable Intent' as a protocol name; it is distinct from the W3C Verifiable Credentials data model, which Mastercard says it will integrate with later.
  • Version drift: the spec headers say 0.1-draft dated 2026-02-18, but main was changed after the v0.1.0 tag (2026-04-17 'BREAKING: field alignment per AP2 schema updates' and 2026-04-20 additions) without a version bump or changelog entry.
  • Terminology inconsistency: the overview's verification lists say merchants verify L1 against the 'Credential Provider's published JWKS', while the credential format says the Issuer signs L1 and publishes the JWKS.
  • The specification uses RFC 2119 keywords.
  • VI is a credential format, not a request protocol, so properties about every request are read as 'every purchase presentation'.
  • The Mastercard announcement page was checked with a web tool; the web tool limits quotes to about 125 characters, so two quotes are sentence fragments.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (66 of 66 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
