Summary

The SCIM Agent Resource draft extends SCIM, the standard that enterprises use to push user accounts from a central directory into the cloud services they use, so that AI agents can be provisioned the same way. A directory can create, update, deactivate and delete an agent's record in a service before that agent ever calls the service. It is an individual Internet-Draft (-00, June 2026) by authors from Microsoft, Okta and Nextident, with intended status Informational. It is discussed on the IETF SCIM working group list but not adopted by it, and it has no named deployments.

The draft defines an Agent resource type at an /Agents endpoint with a small core schema: a required unique agentUserName, a required displayName, a required active flag, an optional description, and an optional list of owners (the users, groups or agents responsible for it). Agents can also be members of SCIM groups, which services commonly map to access rights. The record is sent by the SCIM client (e.g. the enterprise identity provider) to the service over the normal SCIM API. The draft does not define how the agent later authenticates or what it presents on its own requests. It also leaves out credentials, delegation, human approval, model identity and signalling between services.

How it works

  1. The enterprise's SCIM client (typically its identity provider or directory) is already set up to provision accounts into a service, authenticating to the service's SCIM API with an existing method such as OAuth bearer tokens or TLS client certificates.
  2. When an agent is created, the SCIM client sends a JSON Agent resource to the service's /Agents endpoint, with a unique agentUserName, a displayName, active=true and, optionally, owners and a description.
  3. The client can add the agent to SCIM groups. The service decides what access each group gives.
  4. Later, the agent calls the service using some authentication method outside this draft, and the service maps it to the provisioned Agent record by its own rules.
  5. To stop the agent, the SCIM client sets active to false or deletes the record. The service decides what 'inactive' means and how it affects the agent's existing access.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The service can hold an account for each agent and give it access through enterprise-assigned groups. What the agent presents on its requests, and how that maps to the record, is outside the draft.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
The enterprise can deactivate or delete a specific agent in every service it provisions. What deactivation does to existing access is up to each service, and services cannot act on an agent they did not receive from a SCIM client.

Accountability

Goal: an action can be traced back to the parties responsible for it.
An agent record can name its owners (responsible users, groups or agents) and carries a unique name, so actions mapped to the record can be traced to the provisioning enterprise and its listed owners.

Not addressed

  • Neither the Datatracker nor ietf.org could be reached from the analysis workspace. The text was captured from the ietf.org archive .txt through a browser and saved as a snapshot (JSON examples abridged, prose kept). RFC 7644 sections 2 and 3.6 were captured the same way.
  • Related drafts with similar names, not analysed: draft-wahl-scim-agent-schema (AgenticIdentity resource, 2025) and draft-abbey-scim-agent-extension (Agents and AgenticApplications, 2025, expired). Datatracker shows no formal replaces relationship.
  • draft-kushwaha-scim-agent-governance-00 (Oracle, July 2026) is a separate individual draft that extends this Agent resource with lifecycle states (including suspended and quarantined), an autonomy level, validFrom and validTo, and a credential discovery URI. This draft does not reference it, so it is not counted here.

Open questions

  • How is an agent's runtime authentication (e.g. an OAuth client, a workload identity or a certificate) meant to be linked to its Agent record? The draft says only 'subsequently'.
  • Should 'active=false' require the service to revoke the agent's existing tokens and sessions, as the governance draft's states might imply?
  • Is one Agent record meant per agent product, per deployment, or per running agent?
  • Will the SCIM working group adopt this draft, and will roles and entitlements be added to the Agent schema?

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (35 of 35 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-20. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
