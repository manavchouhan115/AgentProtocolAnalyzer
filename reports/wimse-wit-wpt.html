Summary

WIMSE (Workload Identity in Multi System Environments) is an IETF working group defining how software workloads, such as microservices, jobs or AI agents running as services, prove who they are when they call each other. This analysis covers two of its drafts together: the Workload Credentials draft, which defines the Workload Identity Token (WIT) and the Workload Identity Certificate (WIC), and the Workload Proof Token (WPT) draft, which proves possession of the key in a WIT on each HTTP request. Both are working-group drafts (workload-creds-03, October 2026; wpt-02, August 2026), with early implementations listed for SPIFFE, Defakto Security and Teleport.

An Identity Server in a trust domain issues each workload a short-lived WIT, a signed JWT naming its Workload Identifier (a URI) and binding a public key. On each call, the workload sends the WIT plus a WPT signed with its own key, bound to the target URI, the WIT and any user-context tokens, valid for minutes or seconds. The receiving workload checks both against trust anchors configured for that trust domain, then authorizes by the identifier. The drafts leave out authorization rules, user identity (carried in separate tokens such as Txn-Tokens), revocation (short lifetimes instead), contact channels, cross-party signalling and model identity.

How it works

  1. Setup: each trust domain runs an Identity Server; receiving workloads are configured, out of band, with which issuers and trust anchors (e.g. a JWKS or a certification authority) belong to which trust domain.
  2. The Identity Server issues workload A a Workload Identity Token: a JWT naming its Workload Identifier in sub, an expiry (typically hours) and, in cnf, the public key whose private half workload A holds. (For mutual TLS, it can instead hold a Workload Identity Certificate.)
  3. When workload A calls workload B over TLS, it sends the WIT in the Workload-Identity-Token header and a Workload Proof Token in the Authorization header with the WPT scheme. The WPT is a JWT signed with workload A's key, carrying the target URI as audience, a short expiry, a unique jti, a hash of the WIT and hashes of any user-context tokens such as a Txn-Token.
  4. Workload B validates the WIT against the trust anchors for the trust domain in its sub, then checks the WPT: signature with the WIT's key and algorithm, audience against its own configured URI, expiry, WIT hash, token hashes and, as recommended, that the jti is new.
  5. Workload B then authorizes the call under its own policy using the authenticated Workload Identifier (e.g. matching it against access lists) and logs it; the drafts define no permissions format.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The receiving workload can allow or refuse each call based on an authenticated Workload Identifier from a trusted trust domain, under its own policy; the drafts carry no permissions, and user context must come from separate bound tokens.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
Without revocation, a misbehaving workload is stopped by no longer issuing it credentials and waiting for short-lived WITs to expire (typically hours), or by local policy blocking its identifier; deployments may add status lists. No contact or cross-party channel exists.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Each call can be attributed to a Workload Identifier and, if present, the issuer, and logged; instances sharing an identifier cannot be told apart unless the deployment uses jti or per-instance identifiers.

Not addressed

  • Acting for (authority): No; only binds separate user-context tokens (not addressed by the specification)
  • Scoped authorization: No, out of scope (explicitly out of scope)
  • Human approval: No (not addressed by the specification)
  • Revocation: Not defined; short lifetimes instead (explicitly out of scope)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
Yes. Each request carries the WIT (an Identity Server-signed JWT binding the workload's public key) and a WPT signed with that key, which proves possession, so the WIT must not be used as a bearer token. The WPT covers the target URI (audience), an expiry, a unique jti, the WIT hash and hashes of other tokens, but not the HTTP method or body. Alternatively the workload can authenticate at the transport layer with a WIC over mutual TLS (separate binding draft).
Required by the specification · requirement level: MUST
Why this rating: A verifiable proof-of-possession credential on every request (same colour as the three calibration examples).

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Partly addressed
Short but without a number. WPT lifetimes must be short, on the order of minutes or seconds; receivers must reject proofs outside their validity time and should reject WPTs whose expiry is unreasonably far in the future. Yes, within configured trust domains. Authentication and authorization
Authentication of the agent or userDoes the receiving service itself authenticate the party making the request (the individual agent or the user)? Who exactly is authenticated, and by whom?Addressed
Yes, for the calling workload. On each request the receiver verifies a WPT signed with the private key that the Identity Server bound to that workload's identifier in the WIT; the key must be bound to a single Workload Identifier and kept within the workload. The receiver must also compare the identifier with what it expects, since a valid credential alone only proves trust-domain membership. No user is authenticated.
Required by the specification · requirement level: MUST
Why this rating: The service verifies per-request proof from the workload's own key (unlike the three calibration examples, which verify a token issued elsewhere or a provider-level key).

Trust
Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
The Identity Server of the trust domain. Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Not addressed
Not defined. The credentials draft says it defines no revocation mechanism for WITs and does not rely on one; short lifetimes are the primary mitigation. Deployments may add a Token Status List or a deny-list of jti values (then every WIT must carry a jti), with a propagation delay; certificates likewise rely on short lifetimes rather than CRLs or OCSP. Stopping issuance does not invalidate existing credentials before they expire.
Explicitly out of scope
Why this rating: Revocation is explicitly not defined (same as Web Bot Auth); optional deployment mechanisms are noted in the answer.

Notes

  • Analysed together as one protocol at the user's request: draft-ietf-wimse-workload-creds-03 (credentials) and draft-ietf-wimse-wpt-02 (proof of possession). The mutual TLS and HTTP Message Signatures bindings are separate drafts and were not analysed.
  • Name collision: 'WIMSE' is the working group name; the drafts depend on the WIMSE architecture and identifier drafts. The 'WIT' and 'WPT' names were previously part of draft-ietf-wimse-s2s-protocol, which these drafts replace.
  • Quotes were checked against the kramdown source files at the submission tags in the working group's GitHub repository, which the IETF text is generated from; datatracker could not be reached directly from this session.
  • wpt-02 refers to 'Section 5.1.4' of workload-creds for WIT validation; in workload-creds-03 that procedure is the subsection 'Validating the WIT', so the cross-reference may be off by one after renumbering.
  • The drafts use RFC 2119 keywords.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (47 of 47 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
