Summary

ERC-8004, "Trustless Agents", is an Ethereum standard proposal for finding AI agents and judging whether to trust them when there is no existing relationship. It defines three public registries as smart contracts on a blockchain: an Identity Registry that gives each agent an on-chain identifier pointing to a registration file, a Reputation Registry where clients post feedback about agents, and a Validation Registry where independent validators record checks of an agent's work. Its authors come from MetaMask, the Ethereum Foundation, Google and Coinbase. It is a Draft ERC: it reached Review in October 2025 and was returned to Draft in January 2026. Its reference registries are deployed on Ethereum mainnet and several other chains.

An agent's owner registers it as an ERC-721 token (an NFT), whose URI points to a JSON file listing the agent's name and services, such as A2A, MCP, ENS names, DIDs, wallets or an email address, and the trust models it supports. Anyone except the owner can post signed-number feedback and tags, and validators (e.g. re-execution with stake, zero-knowledge proofs, trusted execution environments) can post scores. A service deciding whether to deal with an agent can read these public signals, filtered by reviewers it trusts. ERC-8004 does not authenticate requests, carry credentials, define permissions or revocation, or identify users or models; it is a discovery and reputation layer meant to be combined with protocols such as A2A or MCP.

How it works

  1. The agent's owner calls register() on the chain's Identity Registry, receiving an agentId (an ERC-721 token) whose agentURI points to the agent's registration file, hosted on HTTPS, IPFS or fully on-chain.
  2. The registration file lists the agent's services (e.g. its A2A agent card, MCP endpoint, ENS name, DID, email) and the trust models it supports; optionally the owner proves control of an endpoint domain by publishing a matching /.well-known/agent-registration.json.
  3. A client or service discovers the agent (e.g. by crawling the registry) and interacts with it through the listed protocol, such as A2A or MCP; ERC-8004 does not define that interaction or how the agent proves its identity in it.
  4. Afterwards, clients post feedback (a value plus optional tags and an off-chain file) to the Reputation Registry, and the agent's owner can ask a validator to check its work, which records a 0 to 100 score in the Validation Registry.
  5. Before trusting the agent, a service reads summaries of feedback from reviewers it chooses and validation results from validators it trusts, and decides by its own policy.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
ERC-8004 gives a service public information to help decide whether to engage an agent (its advertised services, feedback from chosen reviewers, validator scores), but no credential or permissions to enforce on requests.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
A service can post negative feedback that other services can read, but there is no revocation or way to cut an agent off; the owner controls its registration and records cannot be deleted.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Registrations, feedback and validations form a permanent public record tied to blockchain addresses (the agent's owner, reviewers, validators); requests themselves are not tied to the agent, a user or a model by this standard.

  • Acting for (authority): No; only the agent's owner address (not addressed by the specification)

IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Partly addressed
Partly. Each agent gets a globally unique identifier: the registry address with its chain (agentRegistry, e.g. eip155:1:0x742...) plus an agentId, the ERC-721 token number. Monitoring and provenance
Cross-party signallingCan one service warn others about a misbehaving agent (shared signals, reputation, abuse reports)?Addressed
Yes, this is ERC-8004's core. Any client except the agent's owner can post feedback about an agent to a public registry, as a value with optional tags (e.g. reachability, success rate) and an off-chain file; every other service can read and filter it. Anyone can append responses, e.g. marking feedback as spam. Signals can be faked by Sybil reviewers, so readers must choose whose feedback to count.
Part of the normal flow · requirement level: MUST NOT
Why this rating: A cross-party signalling mechanism is defined in the core specification (all three calibration examples are red).

Notes

  • The ERC text at commit 503591a contains editor's notes (e.g. on URIStorage and x402) and a commented-out Test Cases section, consistent with its Draft status.
  • The reference contracts at erc-8004/erc-8004-contracts are upgradeable proxies whose upgrade function is restricted to the contract owner; this is an implementation choice, not part of the ERC, but it affects who controls the deployed singletons.
  • Venue is recorded as other: the Ethereum ERC process has editors but is not a formal standards body.
  • The specification file in the contracts repository is identical to the ERC text from the Abstract onward.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (43 of 43 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
