Summary

The Agentic Commerce Protocol (ACP) lets an AI agent, such as ChatGPT, run a purchase against a merchant's own checkout on behalf of a buyer, while the merchant stays the seller of record and keeps payments on its own payment provider. It is aimed at three groups: merchants (called sellers), agent platforms, and payment service providers (PSPs). OpenAI and Stripe maintain it as founding maintainers, with Meta now also listed. It is published on GitHub under Apache 2.0 with dated releases, the latest being 2026-04-17, but the repository still labels the protocol as beta.

ACP is mainly a set of REST APIs that the merchant hosts: the agent creates, updates and completes checkout sessions, sending a bearer API key on every call and, as a recommendation, a signature over the JSON body with a timestamp. Payment details go to the merchant's PSP, which returns a one-time token limited by an allowance (maximum amount, currency, merchant, checkout session, expiry). The merchant can require extra buyer steps such as 3-D Secure, run through a delegated authentication API. ACP does not define how API keys are issued, who vouches for an agent platform, per-agent identity, revocation, contact channels or model identity; request signing is still informally specified.

How it works

  1. Setup, outside the protocol: the merchant and the agent platform agree to work together and set up an API key (the specification does not say who issues it) and, if signatures are used, the accepted signature algorithms. The merchant may also publish a discovery document at /.well-known/acp.json.
  2. The agent (e.g. ChatGPT) calls the merchant's POST /checkout_sessions with the items and, optionally, buyer and address details, sending Authorization: Bearer with the API key, an API-Version and an Idempotency-Key, and as a recommendation a Signature and Timestamp header.
  3. The merchant checks the API key and, if used, the signature and timestamp, then returns the authoritative cart, its payment handlers and any required buyer interventions (e.g. 3-D Secure or biometric).
  4. For card payments the agent sends the card details to the merchant's PSP (POST /agentic_commerce/delegate_payment), which returns a one-time vault token that can only be used within the allowance: maximum amount, currency, merchant, checkout session and expiry time.
  5. If the merchant asks for 3-D Secure, the agent runs it through the delegated authentication API with the merchant's chosen authentication provider, and the buyer may be challenged by the card issuer.
  6. The agent completes the session with the token (and any authentication result). The merchant charges the token through its PSP, creates the order, and sends order updates to the agent platform by signed webhook.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The merchant can allow or refuse an agent platform by its API key, and the payment token limits each purchase to one merchant, one session, a maximum amount and an expiry. It cannot tell individual agents or verified users apart, and the API key carries no scopes.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
A merchant can stop accepting a platform's API key, which cuts off the whole platform and all its users, and payment tokens expire on their own. ACP defines no revocation, contact channel or way to warn other merchants.

Accountability

Goal: an action can be traced back to the parties responsible for it.
An order can be traced to the agent platform (by API key), to the buyer details the agent supplied, and to the payment credential and any 3-D Secure result. Without request signing in practice, the platform's role in a specific request is not provable to a third party.

Not addressed

  • Agent instance identifier: No (not addressed by the specification)
  • Authentication of the agent or user: No, platform API key only (not addressed by the specification)
  • Trust (who vouches for the agent): Bilateral, outside the protocol (handled outside the protocol)
  • Revocation: Not defined; merchant can drop the key (not addressed by the specification)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
A bearer API key on every request, meaning whoever holds the key can use it; it is not proof of possession. The specification also recommends a Signature header (a detached signature over the canonical JSON body) with a Timestamp, but it does not cover the method, path or other headers, and the algorithms are agreed out of band. For payment, the merchant receives a one-time vault token in the complete request, issued by its PSP.
Required by the specification · requirement level: MUST
Why this rating: A defined credential (bearer API key) is required on every request; the answer states it is not proof of possession (same as MCP Authorization).

Notes

  • Name collision: 'ACP' is also used for the Agent Communication Protocol (IBM BeeAI, later merged into A2A), the Agent Client Protocol (Zed, editor to coding agent) and AGNTCY's Agent Connect Protocol. This analysis covers the Agentic Commerce Protocol by OpenAI and Stripe.
  • Version: the latest dated release is 2026-04-17. The RFC design documents in rfcs/ are not snapshotted per release; their headers carry older version dates and statuses Draft or Proposal, and they were read at commit 7fdd78d. Where the RFCs and the released OpenAPI differ, both are cited.
  • Inconsistency: the delegate payment RFC says the client MUST sign requests (section 2.2) but lists the Signature header as RECOMMENDED (section 2.3); the checkout OpenAPI describes Signature as an HMAC for webhook verification, the delegate payment OpenAPI as a detached JSON signature.
  • Most RFC text uses RFC 2119 keywords. Where the requirement tag has an asterisk, the point rests on schema optionality or the lowercase word 'optional' rather than a keyword.
  • Stripe's documentation describes ACP's delegate authentication as delegating authorization with OAuth 2.0, while the specification at this commit defines delegate authentication as 3-D Secure 2 only and lists OAuth 2.0 identity linking as future work. This analysis follows the specification.
  • The OpenAI documentation pages were fetched with a web tool; agenticcommerce.dev could not be fetched in this session.
  • OpenAI's Delegated Payment page (developers.openai.com/commerce/specs/payment) now shows an 'Accept payments' guide for ChatGPT Wallet and the Forwarded header, not the delegated payment specification; older search snippets of that page are out of date, so it was not used as a source.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (64 of 64 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-19. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
