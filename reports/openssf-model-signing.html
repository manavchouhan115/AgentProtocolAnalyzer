Summary

OpenSSF Model Signing (OMS) is a format for signing machine-learning models and datasets, so anyone who downloads a model can check that its files have not been changed and see who signed them. It targets the AI supply chain (model hubs, MLOps pipelines, deployment platforms), not agents making requests. It is maintained by the OpenSSF AI/ML Security Working Group under the Linux Foundation. The specification is at version 1.0 with a conformance suite, though its formal maturity stage is not recorded. NVIDIA's documentation says all models published to its NGC Catalog are signed with OMS.

OMS defines only a thin layer on top of existing standards. A signer lists every file in the model with its hash, wraps that manifest in an in-toto statement, signs it inside a DSSE envelope, and stores it as a detached Sigstore bundle next to the model. The signer can use a bare key, an X.509 certificate chain, or Sigstore keyless signing with a transparency log. A verifier re-hashes the local files and checks the signature against the key, the trusted root CA or Sigstore. OMS says nothing about agents, requests, users, permissions or revocation, and it does not prove which model a running system actually uses. Judged as an agent identity protocol, it covers almost none of the properties, by design.

How it works

  1. A model producer (e.g. NVIDIA for NGC models) chooses a signing method: a long-lived key pair, a certificate from its own PKI, or Sigstore keyless signing tied to an OIDC identity.
  2. The signing tool lists every regular file in the model directory, excluding .git files and the signature file itself, and hashes each file (or each 1 GB shard of large files) with SHA-256 or another registered algorithm.
  3. It builds an in-toto statement whose predicate lists the files and digests, and whose subject is a root SHA-256 digest of the whole manifest, then signs it in a DSSE envelope and saves it as a detached Sigstore bundle (e.g. model.sig).
  4. A model consumer (e.g. a deployment pipeline or inference platform) downloads the model and the bundle and verifies the signature with the public key, the certificate chain against a trusted root, or Sigstore (including the transparency log).
  5. The consumer re-hashes the local files and rejects the model if any listed file is missing or changed, or if unlisted files are present (unless it chose to ignore them). It then decides whether to load the model.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
OMS gives a service nothing to allow or refuse agent requests with. It lets whoever deploys a model refuse to load files that are unsigned or altered.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
No revocation or signalling is defined. If a signed model is found to be harmful, consumers can stop trusting the signer's key or that model's digest on their own.

Accountability

Goal: an action can be traced back to the parties responsible for it.
A verified bundle ties a set of model files to a signer (a key, a certificate holder or a Sigstore identity), with a public log entry for Sigstore signing. It does not tie any agent action to anyone.

Notes

  • OMS is a model and dataset signing format, not an agent identity or authorization protocol. Most rows are red because the rubric looks from the side of a service receiving an agent's request, which OMS does not address by design.
  • The specification uses RFC 2119 keywords.
  • Implementations (sigstore/model-transparency, the model-signing Python package and CLI) are separate from the specification and were not analysed.
  • The README mentions optional embedded metadata predicates (e.g. model version, training data sources) with 'future support coming'. The v1.0 specification does not define them.
  • Some OMS bundle files in the wild use other names (e.g. NVIDIA's documentation downloads result.sigstore), while the spec recommends a .sig extension (SHOULD).
  • Profile maturity is set to 'stable' because the text is labelled Version 1.0, has schemas and a conformance suite, and is in production use. The status row is still yellow because no Approved stage is recorded.

Open questions

  • Has OMS v1.0 been approved as stable? The repository has no tags and the CHANGELOG records no Draft-to-Approved transition.
  • Will a future version define metadata predicates (e.g. model name and version) or a way to bind a signed model to runtime attestation that an agent could present to services?
  • How should a verifier handle a compromised signing key? No revocation guidance is given.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (33 of 33 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-20. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
