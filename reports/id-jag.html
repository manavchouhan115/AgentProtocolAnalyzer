Summary

The Identity Assertion JWT Authorization Grant (ID-JAG), informally called Cross-App Access (XAA), lets an application, such as an AI agent, get an access token for another company's API on behalf of a signed-in user without sending the user through a separate OAuth consent screen. It relies on an identity provider (IdP), e.g. an enterprise single sign-on service, that both applications already trust, so the organisation that runs the IdP decides centrally which applications may reach which other applications for its users. It is an IETF OAuth working group draft (-06, October 2026), edited by authors from Okta and Ping Identity, and still expected to change. Okta implements it.

The application exchanges the user's sign-in assertion at the IdP for an ID-JAG: a short signed token naming the user, the application's client ID at the target, the target authorization server and the granted scopes or resources. The target's authorization server checks the signature, issuer, audience, client and expiry, applies its own policy and issues its own access token; the ID-JAG can optionally be bound to the client's key (DPoP or mutual TLS). The receiving service therefore learns the user and the client application, with scoped access approved by IdP policy. It does not learn the individual agent instance or model, the draft has no per-request user approval, and it defines no revocation, contact or signalling mechanism.

How it works

  1. Setup: the organisation's IdP is trusted by both the client application (e.g. an AI agent) and the resource application's authorization server for single sign-on, and an administrator allows the client to access that resource application for its users with certain scopes.
  2. The user signs in to the client through the IdP; the client receives an identity assertion (an OpenID Connect ID Token or SAML assertion) and optionally a refresh token.
  3. The client sends a Token Exchange request to the IdP with that assertion, naming the target authorization server (audience) and the resource and scopes it wants. The IdP authenticates the client, applies administrator policy and returns a signed ID-JAG, optionally bound to the client's DPoP key or certificate.
  4. The client presents the ID-JAG to the resource authorization server's token endpoint (JWT bearer grant), normally with client authentication. The server checks the type, trusted issuer, signature, audience, client_id, expiry, tenant and any key binding, then applies its own policy.
  5. The resource authorization server issues its own access token, restricted to the granted resources and scopes. The client calls the API (resource server), which validates that token as usual. When the token expires, the client re-presents the ID-JAG or asks the IdP for a new one.

Against the three goals

Access control

Goal: the agent can only reach the resources and perform the actions it is allowed to.
The resource application receives an IdP-approved grant naming the user and the client application, limited by scopes, resources and optional structured details, and can narrow it further by its own policy.

Incident response

Goal: if an agent causes harm, its access can be limited or stopped.
The organisation's IdP can stop issuing new grants for a user or client, but grants and access tokens already issued keep working until they expire; no revocation reaches the resource side, and there is no way to stop one agent instance.

Accountability

Goal: an action can be traced back to the parties responsible for it.
Each access can be traced to the user (sub, tenant), the client application (client_id) and the IdP that issued the grant; not to an individual agent instance or model.

Not addressed

  • Agent instance identifier: No; actor handling out of scope (explicitly out of scope)
  • Authentication of the agent or user: Client app auth; user signs in at IdP (handled outside the protocol)
  • Human approval: No; replaced by IdP admin policy (handled outside the protocol)
  • Revocation: Not defined; IdP can stop new grants (not addressed by the specification)
  • Contact and escalation: No (not addressed by the specification)
  • Cross-party signalling: No (not addressed by the specification)
  • Model identity: No (not addressed by the specification)

Who is being identified?
IdentifierWhat does the agent identifier look like, and what does it actually name (client application, agent provider, the provider's key or URL, a domain, the individual agent)?Partly addressed
Partly. Every ID-JAG must carry a client_id: the client identifier of the application at the resource authorization server, which the server checks against the client that authenticates. It names the client application (e.g. an AI agent product), not an individual agent; it may differ from the client ID used at the IdP, and can be an HTTPS URL when Client ID Metadata Documents are used. An optional act claim can name an actor, but the draft does not define how it is set.
Required by the specification · requirement level: MUST
Why this rating: The identifier names the client application, shared by all its instances (same as MCP Authorization).

Credential and validity
Credential typeWhat credential does the service receive on each request (bearer token, HTTP Message Signature, mTLS certificate, verifiable credential)? What exactly is signed or bound (host, path, time, nonce, body)? Is it proof of possession?Addressed
A signed JWT (the ID-JAG, typed oauth-id-jag+jwt) presented at the resource authorization server's token endpoint, normally together with OAuth client authentication; the API then receives that server's own access token on each request. By default the ID-JAG and the access token are bearer credentials, usable by whoever holds them. Optionally the IdP binds the ID-JAG to the client's DPoP key or mTLS certificate (cnf claim), and the server must then check proof of possession and may bind the access token to the same key.
Required by the specification · requirement level: MUST
Why this rating: A defined, verifiable credential is required to obtain access, and each API request carries the resource server's own token (same as MCP Authorization); proof of possession is optional.

Credential lifetimeHow long is the credential valid? Is the limit a MUST, a SHOULD or unspecified? Is the verifier told to reject longer ones?Partly addressed
Partly. Every ID-JAG must carry an expiry time (exp), and the resource authorization server must reject expired ones, but the draft sets no maximum; the examples use five minutes. The server may refuse ID-JAGs whose expiry is longer than its own policy, or accept each only once. The client may re-present an unexpired ID-JAG to get fresh access tokens, so its lifetime also limits how long access can be renewed without the IdP.
Required by the specification · requirement level: MUST
Why this rating: Expiry is required but no specific limit is given; the verifier may apply its own maximum (MCP Authorization and Web Bot Auth are yellow for the same reason; Visa TAP's eight-minute rule is green).

Scoped authorizationDoes the protocol tell the service what the agent is allowed to do (scopes, per-action limits)? How fine-grained is it?Addressed
Yes. The IdP grants scopes, resource identifiers and optionally structured authorization details (Rich Authorization Requests), based on administrator policy, and writes them into the ID-JAG. The resource authorization server must process them, may narrow them by its own policy, and must restrict the access token to the granted resources. The meaning of each scope is defined by the resource side.
Part of the normal flow · requirement level: MUST
Why this rating: Scoped permissions are part of the normal flow and enforced by the service (same as MCP Authorization).

Trust (who vouches for the agent)Once the credential is valid, why should the service rely on the party behind it? Who vouches for the agent (a central authority, the authorization server and the user's consent, a registry, nobody)?Addressed
The identity provider that the resource application already trusts for single sign-on. The resource authorization server must reject ID-JAGs from issuers it does not trust and must be configured for each trusted IdP. The IdP issues an ID-JAG only when its administrator policy allows that client to act for that user at that target, so a valid ID-JAG means the organisation's IdP vouched for this client and user.

Response and accountability
RevocationDoes the protocol define a way to revoke an agent's access? Who can revoke what, how fast does it take effect at the service, and at what granularity (one instance, one user, a whole provider)?Not addressed
Not defined by the draft. Its design gives the IdP a central cut-off: the resource side should not issue refresh tokens, so renewed access needs a fresh or re-presented ID-JAG, and the IdP should be able to revoke refresh tokens and end a user's sessions. But an ID-JAG already issued stays usable until it expires, and access tokens already issued last as long as the resource server set (the examples use 24 hours). Granularity is per user or client, not per agent instance.
Not addressed by the specification · requirement level: SHOULD
Why this rating: No revocation mechanism reaching the service is defined; the SHOULD-level recommendations only limit renewal at the IdP, so coverage is none (same colour as the calibration examples, which also leave revocation to other parties).

Notes

  • The receiving service is taken to be the resource application: its authorization server receives and checks the ID-JAG, and its resource server (API) receives the access tokens that server issues.
  • The Markdown source has no section numbers, so claims cite section headings; where a heading appears twice (e.g. Processing Rules), the parent section is given in brackets.
  • "Cross App Access" is also Okta's product name, and MCP has an enterprise-managed authorization extension built on ID-JAG. This analysis covers only the IETF draft.

Open questions

  • The draft sets no maximum lifetime for an ID-JAG, and a client may re-present an unexpired one to get new access tokens. How long will deployments let ID-JAGs live, given that this lifetime also limits how fast an IdP-side cut-off takes effect?
  • Future profiles may define actor_token processing and the act claim. Would that give resource applications a per-agent or per-instance identifier?
  • The step-up section still contains a TBD note about requesting the ID-JAG during the authorization request; this may change in later drafts.

About this analysis

The protocol is assessed from the side of the service that receives an AI agent's request (e.g. a website, an API or a merchant), against three goals: access control, incident response and accountability. Each property is rated by what the protocol's own specification defines; features that other standards or parties could add are described but not counted. "Not addressed" does not mean the protocol is flawed: many protocols leave things out on purpose.

Every statement is backed by evidence from the sources (61 of 61 quotes verified word for word against the source). Ratings use rubric v2.1, analysed on 2026-11-18. This report was generated with the protocol-analyzer skill and should be reviewed by a person before it is relied on.
